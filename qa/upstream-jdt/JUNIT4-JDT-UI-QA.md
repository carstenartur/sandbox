# JUnit 4 to Jupiter QA on real JDT UI sources

## Scope boundary

The existing `org.eclipse.jdt.apt.tests` scenario proves only the JUnit 3 to
Jupiter path on JDT Core. JDT Core is predominantly a JUnit 3 corpus and cannot
provide representative evidence for the JUnit 4 cleanup.

A JUnit 4 release claim therefore requires a separate, pinned scenario based on
`eclipse-jdt/eclipse.jdt.ui`, especially `org.eclipse.jdt.ui.tests`. The two
scenarios share provisioning and evidence conventions, but use separate cleanup
profiles, build overlays, named corpus contracts, test inventories and reports.

| Scenario | Upstream corpus | Purpose |
|---|---|---|
| JUnit 3 to Jupiter | JDT Core `org.eclipse.jdt.apt.tests` | `TestCase`, constructors, lifecycle methods and JUnit 3 suites |
| JUnit 4 to Jupiter | JDT UI `org.eclipse.jdt.ui.tests` | annotations, rules, runners, suites, parameterized tests and mixed hierarchies |

Passing the JUnit 3 scenario must never be presented as evidence that the
JUnit 4 migration is complete.

## Reproducibility boundary

The first JUnit 4 scenario uses the already provisioned JDT UI repository:

- repository: `https://github.com/eclipse-jdt/eclipse.jdt.ui.git`
- ref: `R4_40`
- commit: `c922f757b27b7e2b6215db383cec5f8aafd13227`
- Eclipse release: `4.40` / `2026-06`

The JUnit 4 runner must verify this complete pin before reading or changing
source. It must execute the identical upstream test command before and after the
migration and compare test identity, invocation multiplicity, result state and,
where execution order is part of the contract, observed order.

## Initial named acceptance corpus

The initial corpus intentionally contains both migrations that should become
supported and cases that must remain fail-closed until their semantics can be
proved.

### Parameterized runner and field injection

`org.eclipse.jdt.ui.tests/ui/org/eclipse/jdt/ui/tests/quickfix/ConvertLoopOperationTest.java`

This class combines:

- `@RunWith(Parameterized.class)`;
- two public `@Parameterized.Parameter` fields;
- a `@Parameterized.Parameters` factory;
- inheritance from a production type;
- a constructor that calls `super(null)`; and
- a classic JUnit 4 assertion.

The migration must preserve all parameter rows and test invocations. A partial
rewrite of annotations or imports is a failure. If the complete shape is not yet
supported, the preview and report must reject the candidate with a precise
reason instead of changing only the easy parts.

### Coordinated custom `ExternalResource` rule

- `org.eclipse.jdt.ui.tests/ui/org/eclipse/jdt/ui/tests/core/rules/JUnitSourceSetup.java`
- `org.eclipse.jdt.ui.tests/ui/org/eclipse/jdt/ui/tests/search/FileAdapterTest.java`

`JUnitSourceSetup` subclasses `ExternalResource` and implements real workspace
setup and teardown. `FileAdapterTest` consumes it through `@Rule`. This is a
multi-file contract: converting only the rule field or only the resource class
is invalid. Check mode, apply mode, interactive preview and the documentation
scenario must all show the same coordinated candidate set.

### Rule and lifecycle semantics in a reusable base class

`org.eclipse.jdt.ui.tests/ui/org/eclipse/jdt/ui/tests/core/source/SourceTestCase.java`

This class combines `@Rule TestName`, `@Before`, `@After`, mutable project state
and subclasses elsewhere in the project. The planner must inspect the complete
hierarchy and all rule usages. It may migrate only when the selected source
scope is closed and the replacement preserves the test-name and lifecycle
contract.

### JUnit 4 suite

`org.eclipse.jdt.ui.tests/testresources/JUnitWorkspace/JUnit4Tests/src/pack/AllTests.java`

The result must replace `@RunWith(Suite.class)` and `@SuiteClasses` with the
JUnit Platform suite annotations without changing the selected classes or their
order. The test-resource project must still be discoverable by the upstream
JUnit tooling tests after migration.

### Deliberately unsafe custom runner

`org.eclipse.jdt.ui.tests/testresources/JUnitWorkspace/JUnit4Tests/src/pack/Failures.java`

This class combines a custom `OrderedRunner`, a custom order annotation,
`@Ignore`, expected exceptions, passing tests, failing tests and errors. The
cleanup must not remove or replace the custom runner unless the runner and its
ordering semantics are migrated as one proven contract. Unsupported custom
runner semantics must be visible as a named, stable rejection in the report and
interactive preview.

## Documentation-driven acceptance

Documentation and screenshots are part of semantic QA, not post-implementation
polish. They must be developed while the JUnit 4 scenario is being implemented
because producing a truthful walkthrough exposes missing candidate metadata,
unclear rejection reasons, incomplete previews and unusable control flows.

The canonical Help scenario must be generated by SWTBot from the same pinned
Oomph workspace and the same Sandbox product that produced the headless
evidence. It must:

1. open the Cleanup configuration for the real JDT UI project;
2. select the JUnit 4 migration;
3. show the named candidate and every affected file;
4. show whether the candidate is applicable or rejected and why;
5. navigate between affected files without losing the candidate context;
6. display readable before/after diffs for applicable candidates;
7. preserve access to Apply, Back, Cancel and file navigation controls;
8. apply the migration and run the identical upstream tests;
9. capture the resulting Help screenshots automatically; and
10. record repository, ref, commit, project and evidence identity next to the images.

The screenshot test must fail when text is clipped, a control is obscured,
important state is only visible through hover, the selected file is ambiguous,
the preview differs from the headless plan, or the image was produced from a
synthetic source example. A documentation step that cannot explain a rejection
or cannot show the complete coordinated change identifies a product defect.

Screenshots must not be hand-edited into compliance. The product, SWTBot driver,
Help text or migration diagnostics must be fixed and the images regenerated.

## Required evidence

The JUnit 4 scenario must produce at least:

```text
junit4/baseline/                         original JUnit XML reports
junit4/migrated/                         post-migration JUnit XML reports
junit4/corpus/baseline/                  original named JDT UI sources
junit4/corpus/migrated/                  migrated named JDT UI sources
junit4/cleanup-check-report.json         read-only project-wide plan
junit4/cleanup-check.patch               predicted patch
junit4/cleanup-apply-report.json         applied project-wide plan
junit4/migration.patch                   migration-only diff
junit4/candidate-matrix.json             accepted and rejected named candidates
junit4/test-inventory-comparison.json    identity, multiplicity and result comparison
junit4/swtbot/                           UI logs and screenshot provenance
junit4/help/                             generated canonical Help images
junit4/provenance.json                   pins and SHA-256 artifact digests
```

The candidate matrix must distinguish:

- migrated safely;
- rejected because the source scope is incomplete;
- rejected because a rule, runner or hierarchy is unsupported;
- unchanged because no enabled JUnit 4 construct applies; and
- failed because check, preview and apply disagree.

## Integration policy

The headless JUnit 3 foundation and the interactive preview work may remain in
separate, stacked pull requests, but development must proceed as one feedback
loop. Merge order is not development order. The JDT UI JUnit 4 corpus,
interactive preview, SWTBot walkthrough and Help screenshots must be exercised
before either pull request is described as completing the overall JUnit
migration.

A release claim for the JUnit cleanup requires both real-corpus scenarios and
the documentation-driven SWTBot gate to pass on the final integrated commit.
