# Timing the four-input prefix candidate

Frozen after an exploratory calibration pilot selected four inputs and before the formal measurement of an Apply-generated candidate. The three geometries are known development workloads. The pilot does not contribute measurements to this report.

* Obtain candidate source from ordinary scan/Apply on the pinned twelve-file inventory. Verify that both profiles pass the compiler, complete parity, low-level differential, mutable-table and oracle checks. Save the exact upstream-to-generated patch and the complete original and generated source SHA-256 for each changed class. Identical profile overlays share one timing run.
* Compile all upstream sources and benchmark driver once for the original tree, and once with exactly the generated overlay. Use the same JDK, release 21, child heap, virtual CPU count, complete public encode call, seed, byte-for-byte oracles, warmup and windows as the [baseline protocol](../baseline/PROTOCOL.md). The upstream default implementation stays the common reference for both trees.
* For each of the three fixed geometries run all twelve original variants and each generated variant in three independent JVMs. Start from the 108 original job identifiers in the existing `forks.csv` order, append the corresponding jobs of changed variants from that same order, and shuffle the combined list with `Collections.shuffle` and Java `new Random(4711)`. Run one fork at a time. Persist all operation counts, elapsed nanoseconds and allocation counts by window. Use the original aggregation formula to compute median, minimum and maximum rates across the three forks.
* For every candidate and geometry report ratios against its own unmodified implementation, the normal upstream default and the fastest freshly measured original on that geometry. Print each range next to its median. Classify a timing comparison as faster only when the candidate minimum exceeds the comparator maximum, slower only for the converse, otherwise inconclusive. These descriptive range comparisons do not estimate population uncertainty.
* A lower median on any geometry versus the candidate's own original blocks recommending automatic promotion. Passing that condition alone is insufficient for a claim of improved throughput. A claim of a clear advantage over existing implementations requires a candidate range entirely above the best original on the stated geometry. Report every measured class even if it fails the gate.
