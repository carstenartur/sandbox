# Qualifying a complete byte-table accumulation

Use the twelve registered encoders from Backblaze/JavaReedSolomon at `d3c481dc69471e0c47ff6f67f33d53bde941675e` and the existing strict and mathematical profiles. The repository, all twelve source loops and the three benchmark geometries were already known during development.

1. Run the ordinary project scanner and Apply on all twelve classes. Keep the source range, typed reduction, array dependencies, effect order, diagnostics and any applied edits. The first recognition milestone requires a range inside an upstream encoding method that reads a coefficient and a data byte, indexes a two-dimensional lookup table, accumulates using XOR over input shards and writes the result. Single loads, stores, scalar fragments and parity verification methods cannot satisfy this milestone.
2. Compile original sources and each profile's generated overlay. Exercise all twelve public encoders on partial shard buffers, including corrupt parity, and compare all bytes. Exercise each original and its corresponding overlay's low-level encoding method on disjoint arrays, repeated output rows, input/output and coefficient/output aliases, an empty byte range, and a shortened or null row. Compare the exception type and complete mutable data after the call, including writes preceding a failure. Different original loop orders can legitimately observe different values on aliased inputs.
3. For disjoint arrays compare the low-level table encoder output to independent polynomial multiplication modulo `0x11d` and XOR. Qualify the actual multiplication table observed at runtime, along with a one-bit mutation. A table consists of mutable Java arrays. The certificate is specific to the checked values. Exercise differential Java behavior on mutated table contents as well.
4. Only an actual source change produced by ordinary Apply qualifies as a generated candidate. Retain its source hash and exact patch. For each eligible changed encoder, benchmark its compiled overlay and the original, the upstream default and the best original on each of the three fixed geometries. Use the [existing fork/window protocol](../baseline/PROTOCOL.md) and fresh JVMs. Report every candidate and geometry and median, minimum and maximum across forks. If both profiles produce the identical candidate, measure it once. With no source edit the outcome is a recognition/equivalence result and there is no generated-code speed measurement.
