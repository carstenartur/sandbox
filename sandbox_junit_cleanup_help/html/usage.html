Using JUnit Migration

Entry point

Open Java > Code Style > Clean Up, edit a cleanup profile, and select JUnit Migration (Sandbox).

JUnit migration is intentionally not offered under Java > Editor > Save Actions. Its project-wide scope discovery, explicit preview, coordinated changes, and runtime verification are not safe as an implicit per-save editor action.

Choose the execution policy first

  • Leave Best effort disabled for a normal fail-closed migration. This is the recommended default.
  • Enable Best effort only when keeping safe partial progress is useful even though manual completion will be required.

Best-effort mode is never enabled implicitly by a migration preset. Every preset selects a strict, complete option state; Best Effort remains a separate explicit policy choice.

When a transformation is offered

The cleanup requires resolvable JUnit types and only rewrites patterns for which a supported Jupiter equivalent has been implemented. Coordinated rules and fixtures additionally require the complete source lifecycle scope.

Recommended strict workflow

  1. Select a strict migration preset or configure the individual transformations.
  2. Run the cleanup on a version-controlled project or closed source selection.
  3. Inspect every candidate and affected file in the preview before accepting the change.
  4. Compile and execute the same relevant tests used for the baseline.
  5. Compare test identities, counts, states, and parameterized invocation multiplicity.
  6. Expand the scope only after the result is understood.

Atomic coordinated preview

With the pinned optional patched JDT UI host, a coordinated fixture migration and all of its proven @Rule or @ClassRule consumers appear as one candidate-level checkbox leaf. Selecting the candidate shows every required Java file and the Selection is atomic explanation; the contained file changes and edit groups cannot be toggled separately.

  • Enable or disable one complete migration candidate.
  • Disjoint candidates remain independently selectable.
  • Disabling one candidate leaves the other candidate and its files unchanged.
  • Partially disabled nested changes are rejected before execution and by direct perform validation.
  • Applying a selected candidate changes all required fixture and consumer files in one operation; Undo restores them together.
  • Ordinary local cleanup changes retain Eclipse's normal fine-grained preview selection.

The screenshot and candidate-level selection guarantee require the pinned optional patched JDT UI product. Stock or otherwise unpatched Eclipse installations can load the Sandbox cleanup but do not provide this host-side atomicity contract. Do not infer safe partial-selection prevention from a stock preview.

For the distinction between configuration preview, execution preview, independent local deselection, and coordinated atomic migrations, see Cleanup preview model.

Recommended best-effort workflow

  1. Create a dedicated migration branch.
  2. Enable the desired JUnit transformations and the explicit best-effort switch.
  3. Review the preview and the structured diagnostics together.
  4. Apply the change and search the project for Sandbox JUnit migration gap.
  5. Complete every generated @todo marker using its reason code and remediation.
  6. Compile and run the full affected test scope; do not treat a partial source conversion as semantic proof.

Best-effort planning may retain independently proven candidates while rejecting other candidates. It does not make the files inside one retained coordinated candidate partially selectable.

See Best-effort migration and manual completion for marker examples and supported diagnostics.

Screenshot regeneration

The configuration image is generated from a real Eclipse workbench by SandboxHelpScreenshotsSWTBotTest. The atomic candidate image is generated by SandboxAtomicPreviewPatchedJdtSWTBotTest in the separate patched-product workflow. Regenerate the applicable image after UI changes rather than editing either PNG manually.

The screenshot builds are integration tests: they must load the cleanup extension, open the real profile or preview dialog, exercise the documented selection behavior, and package the Help bundle in the product reactor.
