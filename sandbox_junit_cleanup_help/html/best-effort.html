Best-effort migration and manual completion

Enable Best effort: migrate every proven construct and add @todo scaffolds for unresolved gaps only when a partial migration is more useful than an all-or-nothing result. The option is disabled by default and is also disabled for save actions.

What the mode guarantees

  • Independently proven rewrites are still planned and shown in the normal Eclipse preview.
  • An unsupported construct is not replaced by a guessed Jupiter implementation.
  • The original unsupported source remains available for the developer who completes the migration.
  • Each known gap has a stable candidate identifier, reason code, explanation, and concrete remediation.
  • A deterministic TODO with a code example is added to the owning source type's Javadoc, without adding executable members.

When @Rule and @ClassRule fixtures share a source ancestor that extends ExternalResource, best effort marks the connected fixtures and tests. This includes tests that inherit rules, source superclasses that supply test and lifecycle methods, and other fixtures required by the marked tests. These types keep their JUnit 4 discovery and lifecycle behavior until the shared fixture is split into separate instance and class extensions. Independent fixtures and their tests can still migrate together. Assertion rewrites and optimizations of existing Jupiter assumptions can continue in marked files.

JUnit 4 Assume calls stay in place throughout the coordinated source group while a consumer retains Vintage execution, including calls in separate shared helpers. Generated and derived test sources participate in this check even though they are excluded from automatic scope expansion. Calls also stay when the cleanup cannot prove a complete, selected and editable caller scope. This preserves unsatisfied assumptions as aborted tests. Jupiter tests can use these retained helpers. A closed group with no retained Vintage consumer can still migrate its assumptions to Jupiter. Retained parameterized @Test annotations, @RunWith runners and tests inherited from binary libraries also keep the JUnit 4 assumption contract.

A Rule field can refer to a source fixture through a parenthesized construction or a typed factory call. For a fixture with one lifecycle, best effort uses EXTERNAL_RESOURCE_INITIALIZER_UNSUPPORTED when the existing rewrite cannot migrate the fixture and field together. Their connected tests and fixtures stay on JUnit 4 while independently eligible fixtures and tests can still migrate.

What the mode does not guarantee

The resulting project is deliberately allowed to be incomplete. It may fail to compile or its tests may fail until every generated marker is resolved. Selecting this mode is not an assertion that the complete test suite has already been migrated.

Generated source marker

A marker is documentation attached to the affected type. Its method scaffold is a code example, not an unused private method added to the application. It neither executes nor changes test discovery. The candidate, reason, and manual completion instructions remain searchable. For example:

/**
 * @todo Sandbox JUnit migration gap runner:LegacyTest
 *       (CUSTOM_JUNIT4_RUNNER): The runner has no generally equivalent
 *       automatic Jupiter rewrite. Manual completion: port the runner
 *       behavior to one or more Jupiter extensions, or retain Vintage.
 * <pre>
 * private static void sandboxJUnitMigrationTodoCustomJunit4Runner() {
 *     throw new UnsupportedOperationException(
 *         "Manual JUnit migration required: CUSTOM_JUNIT4_RUNNER");
 * }
 * </pre>
 */
public class LegacyTest {
    // Original unsupported constructs remain here.
}

The example is a work item, not a substitute for the missing extension, argument source, lifecycle split, or assertion logic. Remove the TODO only after the corresponding construct has been completed and the relevant tests have passed. Existing marker methods from older cleanup runs are recognized and are not duplicated or silently removed.

Structured diagnostics

The project-wide cleanup application records the same evidence in JSON. Unit locations are represented by opaque identifiers; source paths are not exposed unnecessarily. A gap entry contains:

{
  "candidateId": "runner:LegacyTest",
  "reasonCode": "CUSTOM_JUNIT4_RUNNER",
  "explanation": "The JUnit 4 runner has no generally equivalent automatic Jupiter rewrite.",
  "remediation": "Port the runner behavior to Jupiter extensions, or retain Vintage for this test type."
}

Typical difficult constructs

ConstructWhy automatic conversion may stopExpected manual action
Custom @RunWith runnerThe runner may combine discovery, lifecycle, filtering, and execution semantics.Port the behavior to explicit Jupiter extensions or retain Vintage for the type.
Parameterized provider or injection outside the supported contractThe closed constant-row ParameterizedClass strategy cannot prove every provider or hierarchy.Check the executable boundary; implement an explicit argument source for unsupported cases.
Custom RuleAn arbitrary Rule can wrap statements, alter errors, or control shared resources.Implement the contract as one or more Jupiter callbacks, parameter resolvers, or interceptors.
Fixture used as both @Rule and @ClassRuleOne registration cannot serve both lifecycle scopes; automatic cleanup rejects that mixed use.Retain the fixture implementation and wire separate instance perTest and static perClass registrations with the manual staged bridge, or write dedicated extensions.
Complex ExpectedException matcherThe throwing range and matcher semantics may not map exactly to one assertThrows.Choose the throwing statements explicitly and add Jupiter assertions for message, cause, and state.

Completion checklist

  1. Review every file in the cleanup preview, including unchanged constructs next to transformed code.
  2. Search for Sandbox JUnit migration gap and resolve every generated marker.
  3. Compile the complete affected source scope, not just the changed file.
  4. Run the same test selection before and after the migration and compare test identities, counts, states, and parameter multiplicity.
  5. Regenerate the Eclipse Help screenshot after changing the cleanup UI.
