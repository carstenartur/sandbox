Best-effort migration and manual completion

Enable Best effort: migrate every proven construct and add @todo scaffolds for unresolved gaps only when a partial migration is more useful than an all-or-nothing result. The option is disabled by default and is also disabled for save actions.

What the mode guarantees

  • Independently proven rewrites are still planned and shown in the normal Eclipse preview.
  • An unsupported construct is not replaced by a guessed Jupiter implementation.
  • The original unsupported source remains available for the developer who completes the migration.
  • Each known gap has a stable candidate identifier, reason code, explanation, and concrete remediation.
  • A deterministic marker method is added to the source type that contains or owns the gap.

What the mode does not guarantee

The resulting project is deliberately allowed to be incomplete. It may fail to compile or its tests may fail until every generated marker is resolved. Selecting this mode is not an assertion that the complete test suite has already been migrated.

Generated source marker

A marker is a compilable method body. It intentionally throws when called and contains the exact candidate and reason in Javadoc. For example:

/**
 * @todo Sandbox JUnit migration gap runner:LegacyTest
 *       (CUSTOM_JUNIT4_RUNNER): The runner has no generally equivalent
 *       automatic Jupiter rewrite. Manual completion: port the runner
 *       behavior to one or more Jupiter extensions, or retain Vintage.
 */
private static void sandboxJUnitMigrationTodoCustomJunit4Runner() {
    throw new UnsupportedOperationException(
        "Manual JUnit migration required: CUSTOM_JUNIT4_RUNNER");
}

The method is a work item, not a substitute for the missing extension, argument source, lifecycle split, or assertion logic. Remove it only after the corresponding construct has been completed and the relevant tests have passed.

Structured diagnostics

The project-wide cleanup application records the same evidence in JSON. Unit locations are represented by opaque identifiers; source paths are not exposed unnecessarily. A gap entry contains:

{
  "candidateId": "parameterized:ConvertLoopOperationTest",
  "reasonCode": "PARAMETERIZED_FIELD_INJECTION",
  "explanation": "@Parameterized.Parameter field injection is not represented...",
  "remediation": "Replace field injection ... with explicit Jupiter method arguments..."
}

Typical difficult constructs

ConstructWhy automatic conversion may stopExpected manual action
Custom @RunWith runnerThe runner may combine discovery, lifecycle, filtering, and execution semantics.Port the behavior to explicit Jupiter extensions or retain Vintage for the type.
Parameterized field injectionConstructor or method arguments are not equivalent to mutable field injection in every hierarchy.Create an explicit argument source and pass values to the test method or constructor.
Custom RuleAn arbitrary Rule can wrap statements, alter errors, or control shared resources.Implement the contract as one or more Jupiter callbacks, parameter resolvers, or interceptors.
Fixture used as both @Rule and @ClassRuleOne callback lifecycle cannot be both per-test and per-class.Split the fixture into separate instance and class extensions.
Complex ExpectedException matcherThe throwing range and matcher semantics may not map exactly to one assertThrows.Choose the throwing statements explicitly and add Jupiter assertions for message, cause, and state.

Completion checklist

  1. Review every file in the cleanup preview, including unchanged constructs next to transformed code.
  2. Search for Sandbox JUnit migration gap and resolve every generated marker.
  3. Compile the complete affected source scope, not just the changed file.
  4. Run the same test selection before and after the migration and compare test identities, counts, states, and parameter multiplicity.
  5. Regenerate the Eclipse Help screenshot after changing the cleanup UI.
