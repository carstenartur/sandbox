JUnit Migration: reference

Applicability contract

The cleanup requires resolvable JUnit types and only rewrites patterns for which a supported Jupiter equivalent has been implemented. Project-wide constructs are planned before per-file edits so a fixture, its hierarchy, and all rule users can be evaluated together.

Strict safety model

Strict mode is fail closed. A missing source type, unresolved binding, custom runner, unsupported matcher, external reference, or incompatible lifecycle prevents the affected coordinated migration. The cleanup does not manufacture an extension whose behavior has not been proven.

Coordinated preview-selection contract

A named JUnit 4 resource and every consumer required for its Jupiter lifecycle migration form one immutable candidate. With the pinned optional patched JDT UI host, that candidate is one atomic LTK selection unit.

  • All required resource and consumer files are applied together or not at all.
  • Disjoint migration candidates can be enabled or disabled independently.
  • Required file and edit children are displayed as details, not as independently selectable checkboxes.
  • Fail-closed host validation rejects a partially disabled nested change before execution and on direct perform.
  • Applying one candidate and invoking Undo changes and restores every participating file together.
  • Ordinary local cleanups retain the standard Eclipse file-level and edit-group selection behavior.
  • Save actions remain single-file and do not enter the coordinated preview path.

The candidate-level selection guarantee belongs to the pinned optional patched JDT UI product. The Sandbox wrapper exposes its metadata through a dependency-free reflective bridge and therefore remains loadable on stock Eclipse, but a stock preview does not enforce this atomic-selection contract.

Best-effort safety model

Best-effort mode changes the planning policy between independent candidates, not the atomicity of one coordinated candidate. Proven candidates may be transformed while rejected candidates remain unchanged and receive an explicit manual-completion marker. Files inside one retained coordinated candidate still apply together. Diagnostics state that manual completion is required and explain the exact gap. This mode does not promise a compilable or runnable intermediate tree.

Real-source validation

JUnit 3 and JUnit 4 are validated against different upstream corpora:

  • JUnit 3 migration uses pinned Eclipse JDT Core test sources, which contain the relevant legacy TestCase and suite structures.
  • JUnit 4 migration uses pinned Eclipse JDT UI test sources, which contain Rules, runners, lifecycle annotations, suites, assertions, and parameterization.

A JDT Core run is not accepted as evidence for JUnit 4 migration coverage.

Evidence produced by project-wide QA

  • Exact repository URL, ref, commit, target platform, Java version, and cleanup profile.
  • Baseline and migrated source snapshots for named corpus files.
  • Cleanup check report, apply report, patch, and structured planning diagnostics.
  • Baseline and after-test commands plus the complete JUnit XML inventory.
  • Comparison of test identities, states, counts, and parameterized multiplicity.
  • For best-effort runs, the expected compile/test outcome and every remaining marker reason.
  • For coordinated preview QA, candidate identities, affected-file order, selection state, applied files, and byte-exact Undo.

Known limitations

  • Adding or updating the JUnit Jupiter dependency is a build-system task and is not inferred blindly.
  • Custom JUnit 4 runners and arbitrary Rules may need dedicated migrations.
  • Parameterized field injection and custom providers require an explicit argument-source design.
  • A fixture used as both @Rule and @ClassRule must be split into separate lifecycle extensions.
  • The migrated test suite must be executed; source-level conversion alone cannot validate test semantics.

Support information

The Help content is shipped with the same feature version as the runtime plug-in. When reporting a problem, include the Sandbox feature version, Eclipse version, Java version, the smallest reproducing source, whether bindings were available, the cleanup mode, the structured reason code, and whether the host used the pinned patched JDT UI bundle.
