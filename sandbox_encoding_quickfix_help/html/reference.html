Explicit Encoding: reference

Applicability contract

The cleanup is offered only when the Java AST and bindings identify a supported encoding-sensitive API call and the selected policy provides an unambiguous replacement.

Safety model

Binding-aware matching is used so methods with similar names are not rewritten accidentally. Review behavior-changing policies before applying them to a large code base.

Typed constructors and related sources

Supported Java 10+ Scanner and Formatter calls use Charset overloads, not charset-name strings. Obsolete encoding-exception handling is removed when no surviving operation needs it. File constructors can additionally require IOException; catch and throws changes are planned with source contracts and callers.

Select all affected source files for one cleanup preview, apply and undo. A missing source or fixed external contract is a reported conflict. A handler is not widened when that would intercept unrelated I/O failures. Formatter retains the default FORMAT locale. Save actions do not silently expand their source scope.

Known limitations

  • Dynamic charset names and application-specific fallback behavior are not guessed.
  • A UTF-8 insertion policy can intentionally change behavior on systems whose default charset is not UTF-8.
  • Generated code should still be covered by the project's tests.

Support information

The Help content is shipped with the same feature version as the runtime plug-in. When reporting a problem, include the Sandbox feature version, Eclipse version, Java version, the smallest reproducing source, and whether bindings were available.
