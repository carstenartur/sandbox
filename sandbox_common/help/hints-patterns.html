Patterns, placeholders and rule kinds

Pattern kinds

The engine supports expression, statement, statement-sequence, method-call, constructor, annotation, import, field, method-declaration, block, declaration and type-declaration patterns. Ordinary rules infer their kind from the source syntax. Use @kind when inference would be ambiguous or when a type header must be matched explicitly.

Placeholders

  • $name binds one AST node or identifier.
  • Variadic placeholders such as $args$ and $params$ bind ordered lists.
  • The same placeholder used more than once requires structurally compatible occurrences.
  • Bindings are available to guards, replacement patterns and structured-action values.

Type declaration patterns

@id: remove.legacy.base
@kind: TYPE_DECLARATION
class $type extends legacy.Base {}
=>! removeSupertype(target=$type, type="legacy.Base")
;;

Type-declaration patterns are header-only. An empty pattern body intentionally ignores fields, methods and nested declarations in the candidate. The declared type kind, modifiers, type parameters, record components and supertypes remain constraints. A non-empty pattern body is rejected rather than being interpreted partially.

Classes, interfaces, enums, records and annotation types are supported. The matcher uses AbstractTypeDeclaration and does not cast every top-level type to an ordinary class declaration.

Statement sequences

A statement-sequence pattern preserves order and matches a contiguous sequence. Use it when one replacement depends on several neighbouring statements; do not simulate a sequence by running independent rules that could match different control-flow regions.

Binding quality

Syntax matching can identify candidates, but guards and actions may require resolved JDT bindings. A rule that needs an exact method owner, supertype or declaration must fail when the binding is missing or recovered ambiguously.
