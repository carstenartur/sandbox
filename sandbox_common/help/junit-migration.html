JUnit migration and safety contracts

JUnit migrations range from local annotation or assertion changes to coordinated hierarchy and suite conversions. Sandbox distinguishes these cases so that a local matcher cannot accidentally authorize a project-wide structural change.

Plan-aware JUnit 3 hierarchy migration

The JUnit 3 hierarchy migration first resolves the closed hierarchy and records stable semantic targets. The plan carries facts such as whether a type must lose junit.framework.TestCase, the preserved execution order of a test method, and whether a lifecycle method originally declared @Override.

The bundled hint program then performs the source edits:

  • remove the validated TestCase supertype;
  • add @TestMethodOrder(MethodOrderer.OrderAnnotation.class);
  • add @Test and plan-backed @Order(n) annotations;
  • add @BeforeEach and @AfterEach and remove only the planned lifecycle @Override annotation;
  • qualify or reorder supported assertion invocations.

Fail-closed execution

The rewrite is rejected when the supplied plan contract is missing, the source bindings changed after planning, a required plan value is absent, a structured action targets a different node, or the set of rewritten nodes does not exactly cover the planned targets. A changed annotation shape is not treated as an optional removal.

Execution-tree verification

ExecutionTreeSnapshot captures completed test containers and tests without retaining JUnit or Eclipse model objects. ExecutionTreeComparator applies an explicit policy for identity, nesting, order, results and attributes. Duplicate occurrences are always preserved; there is no set-only comparison that could hide a lost or duplicated test.

Current boundary

The generic plan, action and execution-tree layers are intended to support later JUnit 4 runner, suite, @Rule and @ClassRule migrations. Each new recipe must define its own discovery plan and runtime-equivalence policy instead of adding another Java-side special operation.
