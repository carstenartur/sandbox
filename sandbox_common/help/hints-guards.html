Guards, predicates and composition

Guards add semantic constraints to a syntactic pattern. A source guard follows :: after the source pattern. An alternative guard follows the replacement or structured-action alternative.

Boolean expressions

$receiver.size() == 0 :: hasNoSideEffect($receiver) && sourceVersionBetween(8, 30)
=> $receiver.isEmpty()
;;

Guard expressions use function calls, &&, ||, ! and parentheses. Missing bindings, wrong arity, missing semantic-plan data and rejected type checks evaluate to false; they are not treated as warnings that allow execution to continue.

Local predicates

<!predicate hasOverrideAnnotation($method):
    hasAnnotation($method, Override) ||
    hasAnnotation($method, java.lang.Override)>

void $method($params$) :: hasOverrideAnnotation($method)
=>! removeAnnotation(target=$method, annotation="java.lang.Override")
;;

Predicates provide named, parameterized guard expressions. They may call built-in guards and previously declared local predicates. Predicate names and parameters must be unique in their scope. Cycles, unknown predicates and wrong argument counts are rejected during program parsing.

Common guard groups

  • AST and binding guards constrain resolved owners, types, modifiers, annotations, references and side effects.
  • Source-level guards constrain Java versions and compiler options.
  • Plan guards read semantic roles, typed facts and directed relations.
  • Alternative control uses otherwise() only as an explicit catch-all alternative.

Semantic-plan guards

plannedRole, enclosingPlannedRole
Require a role on the matched, bound or enclosing node.
plannedValue, enclosingPlannedValue
Compare a typed fact on a node or enclosing declaration.
plannedNodeValue, plannedListContains
Compare node-reference and homogeneous list values.
plannedRelation, plannedRelationValue
Require an exact directed relation and optionally one typed relation attribute.
plannedOutgoingRelation, plannedIncomingRelation, plannedRelationCount
Query relation direction and exact multiplicity. Duplicate relation occurrences are intentional and are never collapsed into a set.

Composition guidelines

  • Give a repeated semantic condition a predicate name instead of copying the expression into several rules.
  • Keep predicates project-neutral when they describe reusable AST behaviour.
  • Keep project names and migration roles in recipe files, not in the shared guard engine.
  • Prefer a false result to an approximation when a binding or plan fact cannot be established.
  • Add parser, editor-completion and behaviour tests whenever a guard or predicate feature changes.
