Debugging, tracing and tests

Editor validation

The Sandbox Hint Editor validates metadata, rule terminators, pattern syntax, guards, local predicates, explicit kinds and structured-action schemas. Content assist is derived from the canonical language vocabulary and action catalog. A proposed language feature is incomplete when only the runtime parser understands it.

Debug launch

Use the Sandbox Hint Debug launch type to execute a hint program with debugger integration. The source locator and source-path computer map execution back to the .sandbox-hint program. Breakpoints and trace output should identify the stable rule ID rather than a generated expansion-only name.

Execution console and markers

The Sandbox Hint Execution console reports parsing, matching and rewrite diagnostics. Problem markers identify invalid hint or embedded-Java regions. Execution-trace markers carry the rule ID, hint file, selected replacement and timestamp. Plan-aware diagnostics should additionally state missing roles, values, relations, binding keys or coverage mismatches.

Recommended test layers

  1. Parser contract: valid syntax produces the expected typed model; malformed syntax fails with a source-line diagnostic.
  2. Vocabulary/editor contract: directives, guards, kinds and actions offered by the editor are derived from the runtime catalogs.
  3. Matcher behaviour: positive and negative AST fixtures cover spelling, nesting, binding and source-level boundaries.
  4. Rewrite behaviour: compare complete before/after sources, including imports, comments and formatting-sensitive declaration order.
  5. Plan-aware integration: verify required contract, exact planned target authorization, typed values and stale-plan rejection.
  6. Runtime oracle: when discovery or execution semantics change, compare completed execution trees before and after migration.

Negative tests

For every productive rule, include at least one near miss that must not transform. Important negative cases include unresolved or wrong owners, overload differences, changed modifiers, extra annotations, ambiguous multi-fragment fields, incomplete multi-file scope, absent plan facts and duplicate or reordered relation occurrences.

Execution-tree policies

Use Policy.strict() when semantic container identity and nesting must remain equal. Use sameShape() only when framework container identities legitimately change. leavesInOrder() ignores wrappers but preserves test order and multiplicity. leafMultiset() also ignores order while still preserving every duplicate occurrence. Relax results, attributes or success requirements only in a test that explains why the dimension is irrelevant.

Reproducibility

The complete Maven or Tycho command used by CI must be runnable from a checkout. Workflow-only transformations or hidden generated state are not a substitute for a local build. Keep focused core tests fast, but run PDE tests for JDT rewrite, editor and Eclipse-help integration.
