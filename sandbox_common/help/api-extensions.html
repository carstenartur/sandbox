Extension points and registered services

Hint providers

The org.sandbox.jdt.triggerpattern.hints extension point contributes hint providers to the Eclipse runtime. A provider should return stable, validated programs and must not depend on editor state. Use program IDs and rule IDs that remain stable across formatting or documentation changes.

Guard functions

The org.sandbox.jdt.triggerpattern.guards extension point contributes guard implementations. A guard receives the active match and arguments through the guard contract. It must validate arity and types, avoid mutating AST state, and return false when required semantic information is unavailable.

Guard names form one shared language namespace. Registration must reject conflicting implementations instead of silently replacing a built-in or another extension.

Structured-action schemas

RewriteActionCatalog is the portable schema registry. Extend it with a builder initialized from the standard catalog:

RewriteActionCatalog catalog = RewriteActionCatalog.standard()
    .toBuilder()
    .register(new RewriteActionSchema(
        "replaceSomething",
        Set.of("target", "replacement"),
        Set.of("option"),
        "Replace one validated element"))
    .build();

The parser and editor vocabulary must use the same catalog. Duplicate action names with a different schema are rejected.

Runtime action handlers

Eclipse-side handlers implement StructuredRewriteActionHandler and are registered with StructuredRewriteActionRegistry. The handler name must correspond exactly to a schema. A handler receives a StructuredRewriteActionContext that resolves bindings, literals, plan values, names, class literals and lists and exposes the active JDT rewrite transaction.

Do not register a handler without a schema or document an action without a runtime handler. Registry/catalog drift is a test failure.

Editor and debug integrations

The Sandbox Hint Editor, quick-assist processors, execution console and debug launch type are Eclipse integrations supplied by the common bundle. New language features must update syntax recognition, content assist, diagnostics and debug rendering through shared vocabulary rather than maintaining separate keyword lists.

Choosing an extension mechanism

  • Add a hint provider to distribute new programs.
  • Add a guard for a reusable, side-effect-free semantic predicate.
  • Add an action schema and handler for a reusable AST mutation that cannot be represented safely as a replacement pattern.
  • Add a planner or recipe outside the shared engine when correctness depends on project-specific multi-file discovery.

Compatibility

Extension implementations should depend only on exported API or deliberate runtime-SPI packages. Internal parser and matcher classes are not binary compatibility promises. A change to a schema, guard arity, plan fact type or NodeKey semantics is an API contract change and requires migration tests.
