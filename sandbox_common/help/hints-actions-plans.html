Structured actions and semantic plans

Use a structured action when the rewrite changes declaration structure, modifiers, annotations, supertypes or invocation ownership. Structured actions preserve JDT AST and import-rewrite semantics and are validated against one shared action catalog.

Action syntax

@id: ordered.jupiter.test
void $method($params$) :: plannedRole($method, "TEST_METHOD")
=>! addAnnotation(target=$method,
        annotation="org.junit.jupiter.api.Order",
        value=planValue($method, "testOrder"));
    addAnnotation(target=$method,
        annotation="org.junit.jupiter.api.Test")
;;

Arguments are named. Required, optional, unknown and duplicate arguments are checked during parsing. Actions execute in source order. This order can matter when several nodes are inserted at the same JDT list position.

Action values

  • Quoted strings, booleans and integers are typed literal values.
  • A placeholder such as $method refers to the corresponding pattern binding.
  • planValue($method, "testOrder") reads a typed fact for a planned node.
  • classLiteral("example.Owner.Nested") creates a class-literal annotation value with import handling.
  • name("example.Qualified.Name") represents a Java name rather than a string literal.
  • list(...) creates an ordered homogeneous action value list.

Semantic plan model

SemanticRewritePlan is an immutable authorization graph. Stable NodeKey values identify types, methods, constructors, fields and exact call sites. A plan can assign roles, typed facts and directed relation occurrences with typed attributes. Relation order and duplicate occurrences are preserved.

Binding contract

Ordinary local hints may declare <!binding-policy: optional>, which preserves compatibility when semantic bindings are unavailable. Migrations whose correctness depends on overload, owner, type or hierarchy information must declare <!binding-policy: required>.

Every program with a requires-plan directive is parsed fail-closed: missing, optional, malformed, unknown or conflicting binding policies are rejected before matching or rewriting.

Declaring a plan dependency

<!binding-policy: required>
<!requires-plan: junit3-hierarchy>

@id: hierarchy.root
@kind: TYPE_DECLARATION
class $type extends junit.framework.TestCase {}
    :: plannedRole($type, "JUNIT3_HIERARCHY_TYPE")
    && plannedValue($type, "removeTestCaseSuperclass", true)
=>! removeSupertype(target=$type, type="junit.framework.TestCase")
;;

A plan-aware program is rejected unless a non-empty plan with the required contract is installed. Every structured target must resolve to a stable key authorized by that plan. After matching, exact coverage checks compare the planned targets with the targets for which rewrite operations were produced.

Text versus structured rules

A rule may use ordinary text replacement or structured actions, but a plan-aware rule must not mix both kinds in its alternatives. Split such behaviour into separately identified rules. Text-only rules continue through the established hint rewrite backend; action-only rules create typed AST operations directly.
