Structured actions and semantic plans

Use a structured action when the rewrite changes declaration structure, signatures, modifiers, annotations, supertypes or invocation ownership. Structured actions preserve JDT AST and import-rewrite semantics and are validated against one shared action catalog.

Action syntax

@id: ordered.jupiter.test
void $method($params$) :: plannedRole($method, "TEST_METHOD")
=>! addAnnotation(
        annotation="org.junit.jupiter.api.Order",
        value=planValue($method, "testOrder"));
    addAnnotation(annotation="org.junit.jupiter.api.Test")
;;

The primary matched node is the implicit action target. Use target=$other only when an action deliberately operates on another bound node. Arguments are named and actions execute in source order.

Signature actions accept primitive, imported reference and array types. Generic, wildcard, varargs and void type strings are rejected rather than reparsed as arbitrary Java.

Action values

  • Quoted strings, booleans and integers are typed literal values.
  • A placeholder such as $method refers to another exact pattern binding.
  • planValue($method, "testOrder") reads a typed fact for a planned node.
  • classLiteral("example.Owner.Nested") creates a class-literal annotation value with import handling.
  • name("example.Qualified.Name") represents a Java name rather than a string literal.
  • list(...) creates an ordered homogeneous action value list.

Semantic plan model

SemanticRewritePlan is an immutable authorization graph. Stable NodeKey values identify types, methods, constructors, fields and exact call sites. A plan can assign roles, typed facts and directed relation occurrences with typed attributes. Relation order and duplicate occurrences are preserved.

Plan dependency and bindings

The declaration <!requires-plan: contract-id> is the complete plan-aware safety contract. It both selects the required semantic plan and implies fail-closed semantic target resolution. No separate binding-policy declaration is needed.

Ordinary programs keep the existing compatibility behaviour unless they declare <!binding-policy: required>. Required mode tracks binding-dependent guards as MATCH, NO_MATCH or UNKNOWN. An unknown semantic requirement yields a diagnostic instead of a rewrite, while a decisive logical branch can still determine the result.

Declaring a plan dependency

<!requires-plan: junit3-hierarchy>

@id: hierarchy.root
@kind: TYPE_DECLARATION
class $type extends junit.framework.TestCase {}
    :: plannedRole($type, "JUNIT3_HIERARCHY_TYPE")
=>! removeSupertype(type="junit.framework.TestCase")
;;

A plan-aware program is rejected unless a non-empty plan with the required contract is installed. Every action target must resolve to a stable key authorized by that plan. After matching, exact coverage checks compare planned targets with the targets for which rewrite operations were produced.

Text versus structured rules

Prefer ordinary target code when it fully describes a local transformation. Structured actions are the typed execution form for changes that require plan values, exact target authorization or coordinated AST/import operations. The declaration-diff compiler can derive these actions from supported before/after method declarations without changing their runtime safety contract.
