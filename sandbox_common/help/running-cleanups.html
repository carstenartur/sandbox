Running and reviewing cleanups

Before execution

  • Build the project so that JDT bindings and class paths are current.
  • Select the complete source scope required by coordinated transformations.
  • Commit or otherwise preserve the working tree before applying broad changes.
  • Prefer one coherent cleanup group per review instead of combining unrelated mechanical changes.

Preview and apply

The Eclipse cleanup dialog displays the compilation units that will be changed. Review import changes, modifier order, moved or removed declarations and generated annotations. For a quick assist, compare the proposal preview with the original source before accepting it.

After execution

  1. Build with the same Java level and target platform used by the project.
  2. Run focused tests for the transformed component.
  3. For discovery-sensitive test migrations, run the before/after execution-tree regression rather than checking only whether both test runs are green.
  4. Inspect warnings for unresolved bindings, incomplete scope or skipped candidates.

Batch use

The cleanup application supports apply, check and diff-oriented workflows. Treat its result as the same transformation contract as the IDE: the command-line path must not invent additional rules or silently relax binding checks. A CI job should invoke a reproducible Maven or application command that developers can run locally.

Diagnosing a missing proposal

A proposal may be absent because the project does not meet the minimum Java level, required types are unresolved, the AST shape is outside the documented pattern, a semantic-plan role or value is missing, or the candidate would require an unsafe partial rewrite. Use the Hint Editor trace and validation facilities for DSL-backed transformations.
