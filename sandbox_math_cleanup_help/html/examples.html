Runtime mathematics in real Bouncy Castle code

These are actual Eclipse Clean Up previews for complete, unmodified Bouncy Castle production classes. The inputs u, v, w and x, y, z are unknown runtime values, not constants supplied by the demonstration. The registered cleanup calls Regelsuche, independently verifies the proposed computation, and emits the Java shown on the right.

Not constant folding. Purely static calculations are now left unchanged. A programmer's constant declaration such as int m = 5 * 7 * 11; is not replaced by a magic number. An unchanged runtime output does not justify simplifying a separate constant calculation. Constants can still be operands of a genuine runtime transformation.

What was verified

The production-corpus regression processes five complete source classes: SHA1Digest, SHA256Digest, LongDigest, MD4Digest and MD5Digest. It requires nine verified runtime rewrites, unchanged authored constants, compilable output, exact Undo and no further change on a second cleanup. Original and generated classes are then used in 90 complete digest comparisons across six digest implementations and block-boundary message lengths. Five implementations are additionally compared with the JDK. These execution checks supplement, rather than replace, the independent symbolic proof of each bitvector transformation.

The screenshots have a separate native UI gate: exact full-file preview, visible original and replacement expressions, Apply, binding resolution and byte-exact Undo must all succeed before a PNG and its provenance are retained. The displayed source is not hand-edited after optimization.

Reproduce the profile

In Java > Code Style > Clean Up > Mathematics (Sandbox), enable the explicit cleanup, select int and long, Preserve Java behavior and Lower estimated runtime. The default Only BigInteger profile deliberately does not select these primitive calculations. The examples use 1,000,000 search-work units and 20,000 states. Run Source > Clean Up... and inspect the file preview. The target sources remain Java 17; the Eclipse host uses Java 25.

1. Select bits with complementary masks

// SHA1Digest.f — all three parameters are runtime int values
return ((u & v) | ((~u) & w));
// Actual generated Java
return (w ^ (u & (v ^ w)));

The candidate uses XOR to express selection without an explicit complement. The independent checker proves equality for all 32-bit input values. The same full-file preview also shows the common-mask rewrite in g.

2. Factor a repeated bit mask

// MD4Digest.G
return (u & v) | (u & w) | (v & w);
// Actual generated Java
return (((v | w) & u) | (v & w));

The repeated use of u is factored out of two terms. This is a generic bitwise rule; it is not a method-name or library-specific substitution.

3. Preserve all 64 bits

// LongDigest.Maj — long parameters, used by SHA-384 and SHA-512
return ((x & y) ^ (x & z) ^ (y & z));
// Actual generated Java
return (((y ^ z) & x) ^ (y & z));

The SDK retains the long domain throughout extraction, proof and emission. There is no narrowing, floating-point conversion, new branch or table lookup.

4. Recognize a differently positioned selector

// MD5Digest.G
return (u & w) | (v & ~w);
// Actual generated Java
return (v ^ (w & (u ^ v)));

Here w, rather than the first parameter, selects the bits. Operand order and variable names do not supply the proof.

Source identity and upstream use

The frozen inputs come from the actual Eclipse target source archive bcprov.source-1.85.2.jar, with SHA-256 9b15d2ccb83c76f9f393cb8cb97d0cb971d04dee667cc3f9d7f4ac28f582cb91. The archive entries are under org/bouncycastle/crypto/digests/. Each provenance file records the complete input hash. An archive release is not represented as a checkout of a different Git revision. Bouncy Castle copyright and MIT license.

Review candidates, not measured speedups. Operation counts describe the emitted source, not generated machine code. A JVM may already recognize these identities. The SHA256Digest source even contains an alternative choice expression in a comment. Before an upstream PR, rebase the patch onto current upstream, run its own tests, benchmark the actual call path on supported JVMs, and review maintainability and side-channel properties. The absence of a newly introduced source-level branch is not a constant-time certification. No upstream submission or performance gain is claimed by this gallery.

The cleanup still has a bounded supported fragment. Unknown calls, mutable memory, unsupported numerical contracts and exhausted budgets are diagnosed rather than rewritten speculatively. These examples do not claim that every Bouncy Castle method is optimized.
