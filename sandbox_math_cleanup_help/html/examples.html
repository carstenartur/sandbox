Runtime mathematics in Bouncy Castle

These are native Eclipse Clean Up previews of calculations with unknown runtime inputs. They are not constant-folding examples. The registered cleanup extracts the Java calculation, asks Regelsuche for a less expensive plan, independently verifies it, and emits ordinary Java without an SDK dependency in the edited application.

The four captures show six production methods from a pinned Bouncy Castle checkout. The before/after fixtures are derived from a separate qualification of the complete, unchanged upstream files. For a readable preview, each fixture retains an exact contiguous span of those methods in an otherwise empty original-package class shell. The fixture exporter requires that the real cleanup produce the same result in both contexts. No generated code is hand-edited for the picture.

Fewer operations is not a benchmark result. The independent proof applies to all modeled int inputs, including sign bits. Compilation, original upstream digest tests and additional complete-message comparisons check the actual generated Java. These are separate from the symbolic proof. Neither operation counts nor screenshots establish a measured speedup, unchanged machine-level timing, or suitability of a legacy digest for new cryptographic applications. MD4 and RIPEMD examples are existing maintenance code, not algorithm recommendations.

Reproduce the settings

  1. Open Java > Code Style > Clean Up, edit a profile and select Mathematics (Sandbox).
  2. Enable the explicit cleanup and choose int and long. The initial Only BigInteger profile does not select these methods.
  3. Choose Preserve Java behavior and Lower estimated runtime. The qualified examples use a search work budget of 1,000,000 and 20,000 states. Checked arithmetic is not enabled.
  4. Run Source > Clean Up..., open the preview and select the file. Inspect the complete diff before applying. Eclipse Undo restores the original source.

The host runs on Java 25. Complete upstream originals and generated files are compiled for Java 8 during production qualification; the isolated native preview projects target Java 17. The transformations need no newer Java API. Each image is a full 1280 × 900 native capture with exact Preview, Apply and byte-for-byte Undo assertions.

1. Select runtime bits with fewer operations

MD4Digest.F combines three unknown int arguments. The generic identity below eliminates the explicit complement; it introduces no conditional branch, array lookup, type conversion or arithmetic overflow check:

(x & y) | (~x & z)  =  z ^ (x & (y ^ z))

2. Factor a shared mask in the majority function

MD4Digest.G selects the majority bit from three runtime words. Distributivity permits a shared mask to be evaluated once:

(x & y) | (x & z) | (y & z)
= (x & (y | z)) | (y & z)

The search rule is not tied to MD4: common-mask factoring also applies to supported XOR combinations and long values, subject to independent checking.

3. Independent changes in one production file

RIPEMD160Digest.f2 and f4 use complementary selection with different argument positions. The intervening f3 method is included unchanged. This example exercises multiple independently verified changes rather than one combined all-or-nothing proposal.

4. Different reductions within SM3

SM3Digest.FF1 uses majority; GG1 uses selection. The neighboring GG0 expression remains unchanged. Original rotate expressions elsewhere in the file, including deliberately spelled 32 - rotation constants, are not flattened into magic numbers.

Intentional constants are preserved

A product such as 5 * 7 * 11, a named mask, a constant cast, or an effectively-final chain of constant initializers is not a reason to propose a runtime cleanup. Such source is left unchanged. When a constant subexpression inside a mixed statement cannot yet retain its original spelling, that statement is conservatively left alone and diagnosed as CONSTANT_EXPRESSION_PRESERVED. Other eligible statements remain analyzable. A genuinely runtime-dependent identity such as x ^ x may still simplify to a constant; that is not folding an authored constant formula.

Production qualification and upstream review

The checkout command bash qa/math-optimization/runtime-bouncy.sh PINNED_BC_CHECKOUT FRESH_OUTPUT_DIRECTORY processes complete MD4Digest, RIPEMD160Digest and SM3Digest files. SHA256Digest is a no-change control. It compiles originals and generated classes, runs each unchanged upstream digest test against both versions, compares complete digest outputs across message patterns and chunk boundaries, checks idempotence and exact Undo, and validates exported patches with git apply --check. Source hashes, proof/cost receipts and original JUnit reports accompany the results.

These patches are candidates for human review, not automatically submitted upstream changes. Measure the actual original and generated Java on relevant JVMs and workloads before claiming a performance benefit: a JIT compiler may already implement a similar reduction. Cryptographic side-channel review is separate from numeric equivalence. The cleanup does not promise to optimize arbitrary array arithmetic, field operations or whole algorithms.

All production sources are pinned to bcgit/bc-java commit c314b9cdffa3958a0eff5344f8fdcdb0181ed830: MD4Digest, RIPEMD160Digest, SM3Digest. Exact method spans and whole-file hashes are recorded in every provenance file. Bouncy Castle copyright and MIT license.
