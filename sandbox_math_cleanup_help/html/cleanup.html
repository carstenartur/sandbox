Mathematics Cleanup

Analyze method-local Java calculations with a local, bounded optimizer and an independent numerical checker. The result is ordinary Java. Your application does not acquire a Regelsuche dependency. The cleanup is disabled by default; its initial profile is Only BigInteger with Preserve Java behavior.

Configure, preview and apply

  1. Open Java > Code Style > Clean Up, edit a profile and select Mathematics (Sandbox).
  2. Enable the explicit cleanup. Choose a numeric profile or individual types, then independently choose the safety profile, goal and budget.
  3. Run Source > Clean Up. Read the diagnostics and ordinary file diff before applying. Related outputs belong to one edit group.
  4. Use Eclipse Undo to revert the applied change.

Quick Assist analyzes the current selection in a cancellable background job. When the editor status line reports completion, invoke Quick Assist again to obtain the standard change proposal and preview. Numerical options come from the active project/workspace cleanup profile. Invoking Quick Assist is an explicit analysis request, even when automatic inclusion in cleanup is disabled.

There is no save-action search. Changing the source, compiler settings, classpath, referenced project binding state or mathematics profile invalidates an existing proposal. Analyze the current version again instead of applying old evidence.

Independent options

OptionMeaning
Numeric typesOnly BigInteger; int and long; float and double; or a custom selection of BigInteger, byte, short, char, int, long, float and double. Both declared and actually promoted operation types must be selected.
GoalLower estimated runtime, lower allocation, or readability. An estimated improvement is not a measured speedup.
Work budget / statesDefault 100,000 units of search work and 2,000 states. Allowed maxima are 100,000,000 and 1,000,000. Cancellation and budget exhaustion leave unverified candidates unapplied.
ExclusionsSemicolon-separated path globs, for example **/generated/**;org/example/Secret.java. Excluded files remain unchanged.
Underflow checksExplicitly unsupported. A zero test cannot detect the required tiny-and-inexact event. The disabled control cannot enable it; configuration requesting it is rejected.

Safety profiles

ProfileContract
PRESERVE_JAVAPreserve Java values, integer wraparound, IEEE-754 behavior, relevant exception paths and evaluation effects. No new numerical exceptions are introduced.
GUARDED_FALLBACKA checked, side-effect-free condition selects an equivalent replacement. Otherwise the original calculation executes. The guard and fallback costs count toward the estimate.
CHECKED_THROWA deliberately stricter contract. Numerical violations may raise ArithmeticException. Requires the separate I explicitly accept new ArithmeticException behavior checkbox.
Checked arithmetic changes behavior. Checks must cover both original and replacement operations, including eliminated intermediate values. Integral checks cover modeled range/narrowing obligations; floating-point checks require non-finite-value detection and agreement with the original Java calculation. Unsupported obligations produce a diagnostic, not an unchecked replacement. Select All does not grant checked-mode consent.

What can be analyzed?

InputBoundary
BigIntegerResolved exact-receiver/value-semantics calculations, including multiple statements and outputs. Null behavior, dynamic dispatch, division, modulus and exponent requirements must be justified. Magnitudes must be bounded; mathematically unbounded identities alone cannot justify removing Java implementation-range exceptions. Derived receiver chains must end in a supported value observation. Unknown receivers need supported guards or are rejected; receiver guards are currently unavailable for the lower-estimated-runtime goal and cannot be combined with primitive numerical guard obligations.
byte, short, char, int, longPromotions, concrete widths, casts and operation order remain part of the proof. Existing exact-arithmetic exceptions cannot disappear.
float, doubleOnly concrete IEEE-equivalent transformations qualify. The supported strict contract requires a target Java level of at least 17. Rounding, signed zero, NaN and infinities are not interchangeable with real arithmetic. Only explicitly supported primitive or canonical-value observations qualify; raw-bit and object-identity observations require separate evidence.
BigDecimal, arbitrary Number subclasses, unresolved bindingsNo automatic BigInteger interpretation. Unsupported regions stay unchanged.
Local loop-body calculationsSupported primitive regions can be analyzed inside loops without changing loop control, array effects or external writes.
Effects, mutable arrays, unknown calls, identity observationsNo general algorithm rewrite. A region must satisfy the extractor's explicit local binding, effect and value-semantics checks. External user-defined field constants are rejected because their defining source is not part of the local proof.

Host Eclipse bundles require Java 25. The Java level of the project being edited remains unchanged and limits generated syntax and APIs. Unknown or unqualified target contracts are rejected.

Examples and counterexamples

Four native runtime Bouncy Castle previews show six independently verified production methods, not constant folding. Complete upstream files and their original digest tests are qualified separately from the readable method excerpts used in the native preview.

Intentional constant statements, named constant formulas and effectively-final constant chains remain unchanged. A mixed statement whose constant subexpression cannot yet retain its original spelling is diagnosed as CONSTANT_EXPRESSION_PRESERVED. Eligible neighboring runtime statements remain analyzable. Runtime cancellation such as x ^ x may still legitimately produce a constant.

An eligible shape uses a known BigInteger factory and value-only observations:

BigInteger input = BigInteger.valueOf(a * b);
BigInteger sum = input.add(BigInteger.ONE);
BigInteger result = sum.subtract(BigInteger.ONE);
return result.intValue();

The primitive a * b is evaluated under its existing Java contract. Selecting Only BigInteger does not turn it into unbounded multiplication. An accepted candidate may reuse input for the value of result; the concrete preview includes all retained output and check obligations. Unknown BigInteger parameter receivers or observed object identity need separate evidence and may be rejected.

  • (x * 2) / 2 -> x is invalid for arbitrary Java int inputs: Integer.MAX_VALUE exposes overflow. Checking only the replacement would miss the original overflow.
  • (x + 1) - 1 -> x preserves int wraparound values, but checked mode must still observe an original overflowing addition.
  • (x + 1.0) - x -> 1.0 is invalid for x = 1e16. Both values can be finite and different. A finite test, strictfp, or an arbitrary epsilon does not prove this rewrite.

Headless use and diagnostics

For a strictly read-only analysis, use the separate application with an existing, open Java project in an Eclipse workspace:

eclipse -nosplash -application sandbox_math_cleanup.analysis \
  -data /work/eclipse-workspace \
  --project Example --config /work/math.properties \
  --report /work/math-analysis.json

The application contract is sandbox_math_cleanup.analysis --project NAME --config FILE --report FILE [--apply] [--accept-checked]. The three valued arguments are required; unknown or duplicate arguments are rejected. --project names one existing workspace project, not a path. The configuration and report must use different destinations.

Analysis is the default: candidates are reported without applying source edits. Add --apply to request application. Applying CHECKED_THROW additionally requires both cleanup.mathematics.checkedOptIn=true in the configuration and --accept-checked on the command line. A candidate and an applied change are distinct report outcomes. Estimated costs are not measured timings.

The mathematics configuration has nine strict keys. This example explicitly enables the otherwise disabled cleanup, selects the default numeric/safety profiles, and excludes generated files:

cleanup.mathematics=true
cleanup.mathematics.numericKinds=BIG_INTEGER
cleanup.mathematics.safetyProfile=PRESERVE_JAVA
cleanup.mathematics.goal=LOWER_ESTIMATED_RUNTIME
cleanup.mathematics.workBudget=100000
cleanup.mathematics.maxStates=2000
cleanup.mathematics.checkedOptIn=false
cleanup.mathematics.underflowChecks=false
cleanup.mathematics.exclusions=**/generated/**

Invalid option names or values fail validation. Source/configuration mismatch reports STALE_ANALYSIS. Unresolved bindings, excluded types, unknown effects or domains, absent proofs, cancellation and exhausted budgets produce specific analysis diagnostics. No analyzed user program is executed to infer its behavior.

Qualification status

The real-source screenshot gallery exercises the registered cleanup, native preview, application and byte-exact Undo for four specific examples. The pinned runtime corpus command separately checks complete production files and original upstream digest tests. Whole-library, installation, measured Java performance and cryptographic side-channel qualification remain separate.

The source checkout separates new evidence under qa/math-optimization/results/ from incomplete historical recovery under qa/math-optimization/history/pre-reset/. Earlier corpus outputs and JMH raw samples were lost. Historical aggregate reports are not current measurements and must not be used to claim a speedup.

The benchmark harness compares the actual emitted and original Java with the same rotating inputs, warmup, multiple forks and allocation profiling. Search, proof and code generation are separate development-time work. All generated normalization, guards and checks belong in runtime measurements. A local fixture result does not establish performance for Bouncy Castle or every safety profile.

Numerical equivalence does not certify constant-time behavior. Review secret or unclassified cryptographic regions separately. An analysis result does not authorize automatic cryptographic changes. Public-parameter initialization needs explicit review; constructor arguments are not automatically public. A missing precondition or an unchanged already-optimized file is not a proof of optimality.
