Mathematics Cleanup

Analyze method-local Java calculations with a local, bounded optimizer and an independent numerical checker. The result is ordinary Java. Your application does not acquire a Regelsuche dependency. The cleanup is disabled by default; its initial profile is Only BigInteger with Preserve Java behavior.

Runtime calculations, not constant folding

Authored constant declarations and constant-only changes are preserved. The diagnostic is CONSTANT_EXPRESSION_PRESERVED. Genuine runtime simplification and shared computations remain eligible. See the source-bound runtime Bouncy Castle gallery.

Configure, preview and apply

  1. Open Java > Code Style > Clean Up, edit a profile and select Mathematics (Sandbox).
  2. Enable the explicit cleanup. Choose a numeric profile or individual types, then independently choose the safety profile, goal and budget.
  3. Run Source > Clean Up. Read the diagnostics and ordinary file diff before applying. Related outputs belong to one edit group.
  4. Use Eclipse Undo to revert the applied change.

Quick Assist analyzes the current selection in a cancellable background job. When the editor status line reports completion, invoke Quick Assist again to obtain the standard change proposal and preview. Numerical options come from the active project/workspace cleanup profile. Invoking Quick Assist is an explicit analysis request, even when automatic inclusion in cleanup is disabled.

There is no save-action search. Changing the source, compiler settings, classpath, referenced project binding state or mathematics profile invalidates an existing proposal. Analyze the current version again instead of applying old evidence.

Safety profiles

The separate Mathematical mode checkbox explicitly permits changes to integer overflow behavior and the reference identity of BigInteger results. It is off by default and cannot be combined with checked or fallback profiles. Select All does not grant this consent.

For supported integral calculations, Regelsuche still supplies and verifies the candidate. An additional exact affine proof compares the mathematical functions and computes the old and new local no-overflow domains. For example, 2*x/2 can become x: the former has an intermediate no-overflow domain of [-1073741824, 1073741823], while the latter covers the full int domain [-2147483648, 2147483647]. The old Java expression is also defined outside the smaller interval, but wraps and returns a different result there. This change therefore requires the explicit mathematical opt-in.

The generated method Javadoc records both proven local domains and the changed contract, preserving existing documentation. These domains do not replace other method preconditions. The initial domain checker supports one integral input, affine arithmetic and exact division by a nonzero constant; it does not invent bounds for nonlinear arithmetic, variable divisors or floating point. Ordinary Java optimization runs first; a mathematical retry uses the reserved remainder of the same work budget. Unsupported expressions retain the ordinary Java proof rules.

In mathematical mode, BigInteger return values may be optimized under value semantics. Unproved receivers use exact-type and bit-length checks with unchanged original fallback. Positive-value checks apply to moduli and exponents where needed; zero and negative bases remain eligible. Guard costs count against the estimate. This makes additional expressions eligible; it does not establish that the current SDK has a useful rewrite for every such expression. No increase in BigInteger's supported range or constant-time execution is promised.

A verified real-source example is Bouncy Castle 1.85.2's SimplifiedShallueVanDeWoestijneMapToCurve.process:

// Before
BigInteger tv1 = u.modPow(BigInteger.valueOf(2), p);
// Optimized branch (the emitted code also contains receiver checks and the original fallback)
tv1 = u.multiply(u).mod(p);

The SDK proposes bounded binary multiplication chains for literal modular exponents from 2 through 16 and independently proves modular equivalence. The cleanup includes its receiver checks in the cost assessment. This example does not imply that every modular power, or every cryptographic use, should be rewritten. A fixed allowance for modPow setup is a ranking heuristic, not a measurement of the containing method.

The complete Bouncy Castle scan now finds ten BigInteger changes: four in this curve map, three in Primes, and one each in CramerShoupParametersGenerator, GenericSqrtRatioCalculator and SQIsign's Ibz. Final named constants such as TWO, unshadowed final this fields and incoming local assignments are supported. Identical contract notes appear once per method. See the actual BigInteger preview.

Lower estimated runtime rejects candidates that only improve storage or ordering. Reports include the weighted estimate as well as operation work; sharing repeated evaluations can save work even when the prepared DAG has the same operation count. Neither measure is a benchmark result.

If the SDK's preparation limit prevents a larger source region from entering the search, the cleanup retries smaller regions within the remaining file budget. The report distinguishes this from a completed search that found no improvement; source effects, independent verification and compilation checks still apply to every accepted fragment.

Other effects and control flowGeneral recurrence, virtual numerical summaries, heap/alias analysis and arbitrary algorithm rewrites remain unsupported. A region must satisfy the extractor's explicit local binding, effect and value-semantics checks. External user-defined field constants are rejected because their defining source is not part of the local proof.

BigInteger helper expansion uses the original helper body as input to Regelsuche. For example, a helper returning value.modPow(BigInteger.TWO, modulus) can expose a modular square inside its caller. The generated caller checks the required input conditions and retains the original helper call in its fallback. The helper declaration and its comments remain unchanged when only the caller is selected. Ordinary Java mode does not enable the identity-changing BigInteger helper contract.

Helper arguments are evaluated in their original order, including unused arguments. Unused operations inside a helper remain part of the exception analysis. The JDK constants BigInteger.ZERO, ONE, TWO and TEN are supported; other helper field accesses, arrays, synchronization, recursive calls and general control flow still require additional semantic support. Expanding a helper alone is not sufficient reason to offer a cleanup: the selected optimization goal must improve after counting the required guards.

Host Eclipse bundles require Java 25. The Java level of the project being edited remains unchanged and limits generated syntax and APIs. Unknown or unqualified target contracts are rejected.

Examples and counterexamples

Four real before/after screenshots of runtime-dependent Bouncy Castle calculations show the actual Eclipse cleanup preview, complete pinned production inputs and the required settings. They replace the former constant-only examples. Expected fixture results are test data, never inputs to mathematical candidate generation.

An eligible shape uses a known BigInteger factory and value-only observations:

BigInteger input = BigInteger.valueOf(a * b);
BigInteger sum = input.add(BigInteger.ONE);
BigInteger result = sum.subtract(BigInteger.ONE);
return result.intValue();

The primitive a * b is evaluated under its existing Java contract. Selecting Only BigInteger does not turn it into unbounded multiplication. An accepted candidate may reuse input for the value of result; the concrete preview includes all retained output and check obligations. Unknown BigInteger parameter receivers or observed object identity need separate evidence and may be rejected.

  • (x * 2) / 2 -> x is invalid for arbitrary Java int inputs: Integer.MAX_VALUE exposes overflow. Checking only the replacement would miss the original overflow.
  • (x + 1) - 1 -> x preserves int wraparound values, but checked mode must still observe an original overflowing addition.
  • (x + 1.0) - x -> 1.0 is invalid for x = 1e16. Both values can be finite and different. A finite test, strictfp, or an arbitrary epsilon does not prove this rewrite.

Connected local calculations and source provenance

Whole-file analysis in PRESERVE_JAVA can connect up to four original calculation regions across unchanged call statements in the same block. Select the primitive integral types involved, with mathematical mode off. Only initialized, effectively final local values and total integral expressions qualify; array/field accesses, division/remainder, mutation and general control-flow changes retain their boundaries. A call that observes a produced intermediate prevents connection. The call itself is not assumed pure and remains in its original order, even when it throws.

Accepted connected computations carry one proof and an atomic group of small JDT edits. Unchanged call statements and comments are not swallowed by a large replacement edit. Recorded sourcePlan data contain source-version hashes, node and binding descriptors, original occurrence IDs and exact edits; Eclipse node objects are resolved only within the adapter, not stored in the mathematical AST. A changed source or project environment requires reanalysis. Selection-only Quick Assist retains its existing region boundaries.

Source discovery and search share the file work allowance. When a joint proposal cannot be applied, the original regions are retried within the remaining allowance; unsupported connections never authorize a fallback that repeats side effects. Diagnostics now carry a stage distinguishing source, search, proof, emission, cost and budget boundaries. An ambiguous SDK rejection remains SEARCH_OR_PROOF, not a fabricated cause. This connected-source fragment is not general SSA, alias analysis or BigInteger motion; separately admitted counted-loop motion is described below.

Java callable and iteration contexts

With primitive integral kinds selected, PRESERVE_JAVA and mathematical opt-in off, numeric block/expression lambdas use the nearest resolved SAM return type. Conditional arms, switch yields, unbraced returns/assignment RHSs and numeric comparison operands in primitive predicates can be simplified in place. Exact expression types, functional targets and enclosing overloads are rechecked. Conditions, selectors and short-circuit positions remain unchanged.

Pure ULR numeric inspection is separate from converter rendering. Adjacent expression-map kernels on known sequential ordered JDK Int/LongStream sources can fuse while preserving the source and sum/reduce/min/max terminal. Total local primitive arithmetic and the same intermediate width are required. Unknown factories/proxies, filter/peek/mode stages, block maps, reads/calls and floating fusion remain excluded; inspection does not authorize stream-to-loop conversion.

Canonical fixed-count for, enhanced-for, while and do loops can move one direct initializer/RHS invariant per loop into a final primitive temporary. Exact counts, available unwritten local inputs, total integral arithmetic, Block placement and strict cost gain are required. Loop controls remain unchanged. Reads, calls, unboxing, division, floating work and recurrences cannot move. Expression-only callable/branch sites cannot add capture statements; ordered reads require their own straight-line capture positions.

Loop scheduling has a separately replayed source receipt. The SDK proves one numerical evaluation; it does not prove the loop schedule. Cost counts the temporary store, per-iteration reads and retained storage. When pinned array effects may throw, the estimate is conditional on normal loop completion. Operation counts are not measured speedups. General recurrence, virtual-call, heap and BigDecimal proof models remain additional work.

Headless use and diagnostics

For a strictly read-only analysis, use the separate application with an existing, open Java project in an Eclipse workspace:

eclipse -nosplash -application sandbox_math_cleanup.analysis \
  -data /work/eclipse-workspace \
  --project Example --config /work/math.properties \
  --report /work/math-analysis.json

The application contract is sandbox_math_cleanup.analysis --project NAME --config FILE --report FILE [--apply] [--accept-checked]. The three valued arguments are required; unknown or duplicate arguments are rejected. --project names one existing workspace project, not a path. The configuration and report must use different destinations.

Analysis is the default: candidates are reported without applying source edits. Add --apply to request application. Applying CHECKED_THROW additionally requires both cleanup.mathematics.checkedOptIn=true in the configuration and --accept-checked on the command line. A candidate and an applied change are distinct report outcomes. Estimated costs are not measured timings.

The mathematics configuration has twelve strict keys. This example explicitly enables the otherwise disabled cleanup, selects the default numeric/safety profiles, and excludes generated files:

cleanup.mathematics=true
cleanup.mathematics.numericKinds=BIG_INTEGER
cleanup.mathematics.safetyProfile=PRESERVE_JAVA
cleanup.mathematics.goal=LOWER_ESTIMATED_RUNTIME
cleanup.mathematics.workBudget=100000
cleanup.mathematics.maxStates=2000
cleanup.mathematics.timeoutSeconds=5
cleanup.mathematics.checkedOptIn=false
cleanup.mathematics.mathematicalOptIn=false
cleanup.mathematics.underflowChecks=false
cleanup.mathematics.explanations=NONTRIVIAL
cleanup.mathematics.exclusions=**/generated/**

Invalid option names or values fail validation. Source/configuration mismatch reports STALE_ANALYSIS. Unresolved bindings, excluded types, unknown effects or domains, absent proofs, cancellation and exhausted budgets produce specific analysis diagnostics. No analyzed user program is executed to infer its behavior.

Qualification status

The real-source screenshot gallery exercises the registered cleanup, native preview, application and byte-exact Undo for five specific examples. Matched 2026-10-31 BC scans at the frozen local code revision accepted 146 strict and 147 mathematical regions, retaining all baseline spans; SWT ImageData remained at zero. The mathematics suite passed 714 tests with one existing optional skip. Native packaging/SpotBugs passed; workbench execution, installation and measured Java performance remain separate from these results. Repository policy passed 12 tests at documentation checkpoint 13638a03. Final independent branch review approved draft integration without open findings. The complete work is published in draft/reference PR #1772; exact-head CI and the required split before merge remain separate integration gates.

The source checkout separates new evidence under qa/math-optimization/results/ from incomplete historical recovery under qa/math-optimization/history/pre-reset/. Earlier corpus outputs and JMH raw samples were lost. Historical aggregate reports are not current measurements and must not be used to claim a speedup.

The benchmark harness compares the actual emitted and original Java with the same rotating inputs, warmup, multiple forks and allocation profiling. Search, proof and code generation are separate development-time work. All generated normalization, guards and checks belong in runtime measurements. A local fixture result does not establish performance for Bouncy Castle or every safety profile.

Numerical equivalence does not certify constant-time behavior. Review secret or unclassified cryptographic regions separately. An analysis result does not authorize automatic cryptographic changes. Public-parameter initialization needs explicit review; constructor arguments are not automatically public. A missing precondition or an unchanged already-optimized file is not a proof of optimality.

Explain a verified change

Source explanations selects no source comments, comments for nontrivial changes (the new-profile default), or comments for every change. The description uses actual Java names and the independently checked original/replacement value graphs. It identifies premises and numerical policies, not a hand-written example template. Detailed diagnostics and the JSON report retain these plans even when source comments are disabled. Existing nine-argument programmatic option construction remains comment-free.

The CLI key cleanup.mathematics.explanations accepts NONE, NONTRIVIAL, or ALL and defaults to NONTRIVIAL.

With mathematical mode enabled, explanations retain the verified local domain and any changed overflow or BigInteger reference-identity contract. Such contract changes are nontrivial even when the original calculation has few operations.

A value-graph comparison is not a complete step-by-step search derivation. Existing source-trace and Java checks still govern evaluation order and exceptions. Checked arithmetic is an explicit contract change; operation estimates are not timing measurements. No source-comment setting re-enables constant-folding-only edits.

Recorded mathematical search steps

The explanation includes the selected Regelsuche search path: each step names the actual rule and displays the resulting computation using your Java variable names. The SDK checks the contiguous path, regenerates its rule applications and independently checks its numeric equivalence before Sandbox presents it. No target formula or source-specific mathematical task is supplied by this view.

A compound proposal remains one recorded search step; it is not expanded into unrecorded primitive identities. Legacy candidates without a recorded path are explicitly identified. The original Java evaluation trace, numerical profile, guards and fallback remain authoritative. Estimated work is not a timing measurement.

The existing Source explanations setting controls Java comments. Detailed diagnostics and JSON reports retain the same selected path when source comments are disabled. Cancellation or an oversized explanation never produces a silently truncated path.
