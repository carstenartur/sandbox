## Ordered, immutable published identity

Use source identity for snapshots. For validated main commit H, set the support-module qualifier to `v<12-digit-zero-padded-first-parent-height>-g<full-lowercase-40-hex-H>`. Height is `git rev-list --first-parent --count H` on the full validated history. Reject shallow history, overflow and an unexpected checkout. A fast-forwarding first-parent main sequence increases the numeric field even across same-minute commits, clock regressions and CI reruns. The SHA binds the selected revision. OSGi compares the qualifier lexically: `1.3.11.SNAPSHOT < 1.3.11.v000000001234-g… < 1.3.11.v000000001235-g… < 1.3.11.zRelease`. Bare numeric timestamps would sort below the legacy literal. Use `zRelease` for the released support bundle of that numeric base. The next numeric micro outranks all qualifiers on its predecessor. This ordering applies to the support IU. Existing stable aggregate/feature versions become unqualified under stable version rewriting, so automatic same-base snapshot-channel to stable-channel updates of the *whole product* are outside this proof.

Set `forceContextQualifier` in the **support module's plugin execution** from a dedicated property such as `sandbox.support.qualifier`. Provide a module-local Tycho UTC fallback format `'dev'yyyyMMddHHmmssSSS` when the property is absent for standalone and normal PR builds. Accept the dev channel only for build/test installation, and reject it for publication. Explicit release/snapshot build adapters provide the publishing value. Avoid passing global `-DforceContextQualifier`, which would requalify other bundles. Set `-Dproject.build.outputTimestamp=<validated commit epoch seconds>` on publishing builds so a rerun can reproduce the JAR, then actually compare the bytes. Echo the source ref, SHA, height, exact OSGi version, SHA-256, and source CI run ID in a receipt. A retry at the same support identity with different bytes fails.

In `.github/workflows/deploy-snapshot.yml:85–97,116–150,185–212,283–291`, use the existing validated SHA, full fetch, serial publication and prior Pages checkout. Put the support receipt beside the snapshot build manifest and in existing verification evidence. Before replacing latest, a small Java validator compares the currently published repository/receipt against the candidate. Allow initial introduction when the old metadata genuinely contains no support IU. Once present, require receipt, actual hashes and matching manifest identities. For a same-source retry require identical support version and SHA, non-regressing component and aggregate versions, and identical corresponding feature JAR bytes wherever those versions are equal. Publish the verified candidate via the existing workflow. For advancing builds require a descendant on the first-parent main chain, a strictly newer support version and strictly newer containing feature/aggregate versions, otherwise fail before the Pages mutation. The latter guards same-minute/reordered parent updates while leaving their existing packaging alone. Read previous source SHA from the prior build manifest (`.github/scripts/generate_build_manifest.py:229–250`). A broken receipt is a failure, not a fresh introduction. Stable workflow already makes an immutable release commit and rejects existing tags/releases (`.github/workflows/deploy-release.yml:167–174,220–253`); pass the release qualifier and its commit timestamp to the distribution build. Keep shells as thin provenance/Maven adapters. Tests and semantic checks belong in Java.

Pinned primary implementation confirms this mechanism. In `tycho-packaging-plugin-5.0.4.jar!META-INF/maven/plugin.xml:18–28`, the build-qualifier descriptor explicitly covers regular Maven projects, exports `buildQualifier`, `unqualifiedVersion`, `qualifiedVersion` and defaults to validate. Direct inspection of `BuildQualifierMojo.execute/getUnqualifiedVersion` shows writes to the Maven project properties and the numeric Maven-version fallback for `-SNAPSHOT`. Bnd 7.3.0's `AbstractBndMavenPlugin.execute` imports those project properties. In `tycho-core-5.0.4.jar`, `BundlePublisher.getBundleIU` (embedded source line table 52–69) reads the original bundle description, keys the IU from its BSN/version and passes the original file into `FileArtifactRepository.forFile`. Tycho publication therefore cannot repair a literal `.SNAPSHOT` manifest after packaging. First implementation check: run a clean standalone package with an explicit sample publishing qualifier and assert the resulting manifest and repeated SHA, then run the ordinary standalone build to test its fallback. The addendum confirms the stable path with a separate minimal Maven JAR build.

## Addendum — stable qualifier and snapshot retry decision

**Stable Maven qualification was exercised.** An independent ordinary Maven JAR with POM version `1.3.11`, `tycho.mode=maven`, explicit validate-phase Tycho 5.0.4 `build-qualifier` execution forcing `zRelease`, Bnd 7.3.0 `Bundle-Version: ${qualifiedVersion}`, and the Maven JAR manifest handoff was built twice offline in two initially empty output directories. Both logs report `The project's OSGi version is 1.3.11.zRelease`. Both packaged manifests contained `Bundle-Version: 1.3.11.zRelease`. With the same fixed output timestamp, SHA-256 for both complete test JARs was `5dea56cbe29c4e23687e8e39078bcb89b85e7e5c218986fe68f0353182a66068`. This proves plugin interpolation for an ordinary stable Maven project. The real support artifact still needs its own identity, reproducibility and installation checks.

Tycho's distinct handling of Tycho-packaged artifacts explains the potential ambiguity. The source line tables in the pinned binary show `AbstractVersionMojo.getOSGiArtifact/getOSGiVersion` (44–45, 54–58) returns null without a Tycho project type. `BuildQualifierMojo.calculateQualifiedVersion` (166–188) preserves a pre-existing concrete OSGi version only when it actually obtained one through that path. The ordinary JAR uses the forced qualifier, while its Maven version supplies the numeric base. `TychoProjectVersion.getOSGiVersion` (290–293) appends the nonempty qualifier. The release Maven GAV can therefore stay `1.3.11` while the support bundle version is `1.3.11.zRelease`.

**Snapshot gate decisions.** Before the existing Pages mutation, compare the candidate with the checked-out `snapshots/latest` that it would replace. On success deploy this candidate, publish its own provenance and validate the live site against its freshly built `target/distribution-verification/verification.json` as required by `.github/workflows/deploy-snapshot.yml:252–262`. The existing post-deploy verification and rollback cover every successful preflight, including retries. A failed preflight stops before mutation.

| Relationship to the published snapshot | Preflight requirement |
| --- | --- |
| Same validated source SHA | Require valid receipts and exactly the same support BSN, OSGi version and full JAR SHA-256. Compare the JUnit cleanup feature group and aggregate group independently. Each candidate version must be at least its published counterpart. When versions are equal, compare SHA-256 of both complete corresponding feature JARs from their repository artifact keys and require identical bytes. A greater enclosing version is allowed. Verify that the candidate dependencies point to the actual candidate members. |
| Advancing first-parent descendant, previous snapshot contains support | Require verified current/candidate receipts and strictly increasing full OSGi versions for support, the JUnit cleanup feature and the aggregate. Verify candidate dependency identities and correspondingly keyed artifacts. Equality of either enclosing version fails even if its bytes match. |

This is the only case that can lack an earlier support receipt. |

## Qualification correction

The first real product wired the unchanged support imports to Jupiter 6.1.3 while JDT 5 used 5.14.4. Constraining the cleanup consumer alone reproduced the mismatch. A manifest-only fragment supplied by the component feature constrained the support host to Jupiter 5/Platform 1. Equinox reported both host and fragment requirements on the same provider for each package and all five class identities matched the runner. The standalone JAR retains its original import ranges. The reconstructed historical stage reports whichever installed JDT generation actually binds its original APIs. Only the new feature stage requires the JDT 5 binding fragment and all four factories.
A later consumer target/API check must compare actual provider identities and reject an incompatible native JDT 6 target until that class space has its own verified solution. Ordinary JUnit 6 classpath tests and native JDT 5 product tests provide separate compatibility evidence.
