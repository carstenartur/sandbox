# Eclipse Help evidence coverage

This matrix defines which evidence is required for each user-facing Sandbox surface. It prevents a cleanup-profile screenshot from being mistaken for proof of an executable source change.

## Evidence types

- **Configuration**: where the feature is enabled and which policy or mode is selected.
- **Source semantics**: compact, reviewed before/after examples plus applicability and rejection boundaries.
- **Real execution preview**: the actual Eclipse LTK file/candidate tree and source comparison, exercised through Apply and Undo.
- **Task UI**: a feature-specific wizard, Quick Assist, view, preferences page, or context action that is not represented by the common Java Cleanup preview.
- **Nonvisual evidence**: command/output examples where a screenshot would be decorative or misleading.

The standard local LTK frame is a shared Eclipse host surface. JFace supplies the canonical real local-preview evidence because its fixture proves combined changes, switching source comparisons, independent file deselection, Apply, and byte-exact Undo. Local cleanup families do not duplicate the same host frame; they document their own source semantics with concrete examples. Coordinated Int-to-Enum and JUnit migrations have distinct candidate-selection semantics and therefore require their own real preview images.

## Merge and release gates

1. Every shipped PNG is referenced by HTML in the same Help bundle.
2. Every screenshot-generating scenario asserts the semantic UI state before capture.
3. Distinct documented states must produce distinct image digests.
4. Real preview images must differ substantially from configuration-tab images.
5. Generated bytes are staged with SHA-256 manifests before an intentional baseline mismatch fails CI.
6. Baseline images are imported only from a completed reference-environment run and visually inspected.
7. The next release must package the same reviewed Help and images that passed these gates.
