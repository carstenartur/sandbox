## Proposed contents

Use [the curated release notes](../../release_notes.md). This preparation changes
documentation only. The candidate includes merged converter correctness fix #1776
and the now-merged optional math-first coordinator #1778. The combined operation is
off by default, uses Preserve Java behavior with Mathematical mode off, and keeps
one file preview/change group/Undo with shared work and time budgets. Source,
project-setting or effective-profile changes invalidate a prepared result.
The ordinary converter remains independently usable; no save action is added.

The candidate also includes merged [#1782](https://github.com/carstenartur/sandbox/pull/1782)
(`9fac143dda1a2708a74da132af814394348361a3`), which updates the qualified
vendored value-arithmetic SDK, native Help provenance and retry-budget test
coverage. The later Java adapter integration is separate from that prerequisite.
Merged [#1783](https://github.com/carstenartur/sandbox/pull/1783)
(`d06ffc85a56ec61968ac2eee28031924ddd3368a`) adds the bounded neutral ULR state
model, direct primitive tail-recursion inspection, and an internal source-only
loop planner with independent typed replay. It requires explicit
`ALLOW_FRAME_ELISION`; preserving numeric state does not preserve stack/resource
behavior. Source-snapshot Apply/Undo is not native Eclipse lifecycle integration.
As documented in [TAIL_RECURSION.md](../../sandbox_math_cleanup/TAIL_RECURSION.md),
this slice adds no cleanup checkbox, default profile, Quick Assist or save action.
Native Converter/UI integration, value-object summaries, affine/matrix extraction
and mathematical iteration replacement remain outside this candidate's foundation.

The current mathematics SDK is pinned in
[sandbox_math_cleanup/lib/qualification.json](../../sandbox_math_cleanup/lib/qualification.json)
and its [provenance README](../../sandbox_math_cleanup/lib/README.md):

- Source `93f0f35abaea58ea492441776be7c9d2a9be1695`.
- Standalone JAR `5ad54860d828a738d4df8dba87659b8a14009bfb208f79705a4b8529b9c58884`.
- Version `0.5.1-issue1657-93f0f35abaea`, not publicly published as an SDK artifact.
- Source tree `673af46945cf0389af0c0521e23e52616ef49351`.
- The current [reproducibility receipt](../../sandbox_math_cleanup/lib/reproducibility-2026-11-01-published-value.json)
  records two clean local SDK builds, 302 SDK tests per build, two fresh external
  consumers and ten byte-identical distribution files. This is local source-bound
  SDK qualification, not remote CI or an Eclipse product/distribution result.
- Historical finite-series receipts remain preserved with their original source
  identities and digests; they do not describe the current JAR.
- The bundle packages the checked-in JAR through Bundle-ClassPath and lib/.
  Generated application Java has no SDK runtime requirement.

A new Regelsuche public release is optional for this exact artifact. Updating

JGit storage 0.11.8 is already released and pinned, so no new library release is needed.

## Existing execution path after review and publication approval

Use the existing **Release Workflow** in
[deploy-release.yml](../../.github/workflows/deploy-release.yml), on main.

First dispatch the existing diagnostic build with:

| Input | Value |
| --- | --- |
| release_version | `1.3.8` |
| next_development_version | `1.3.9-SNAPSHOT` |
| next_version_increment | `patch` (overridden by the explicit next version) |
| skip_tests | `false` |
| dry_run | `true` |

The workflow always checks out main, even when dispatched from another ref. A
dry-run before merging preparation/correctness changes cannot validate that branch.
The dry-run still builds/verifies a temporary stable tree and archives and uploads
evidence; its publication operations are guarded by `DRY_RUN != 'true'`.

When the final candidate and diagnostic evidence are approved, the separately
authorized publication run uses the same inputs with `dry_run=false`.
It builds/verifies the stable tree, deploys and verifies the versioned p2 repository,
creates the tag and draft Release, verifies archives, then publishes and opens
the next-development PR. These publication operations are not performed here.

The workflow generates `release-notes.md` from commit subjects; it does not read the
curated `release_notes.md` in this preparation. Incorporate this draft explicitly
in the publication review or make a separately tested workflow change before
publication if automated use is desired. Do not assume it is automatically consumed.

Do not create a `release-request/**` branch or `.github/release-request` marker
during preparation: that existing push path initiates publication with no dry-run
input. Marketplace/Zenodo verification follows the existing publication workflow.
