## Existing execution path after review and publication approval

Use the existing **Release Workflow** in
[deploy-release.yml](../../.github/workflows/deploy-release.yml), on main.

First dispatch the existing diagnostic build with:

| Input | Value |
| --- | --- |
| release_version | `1.3.8` |
| next_development_version | `1.3.9-SNAPSHOT` |
| next_version_increment | `patch` (overridden by the explicit next version) |
| skip_tests | `false` |
| dry_run | `true` |

The workflow always checks out main, even when dispatched from another ref. A
dry-run before merging preparation/correctness changes cannot validate that branch.
The dry-run still builds/verifies a temporary stable tree and archives and uploads
evidence; its publication operations are guarded by `DRY_RUN != 'true'`.

When the final candidate and diagnostic evidence are approved, the separately
authorized publication run uses the same inputs with `dry_run=false`.
It builds/verifies the stable tree, deploys and verifies the versioned p2 repository,
creates the tag and draft Release, verifies archives, then publishes and opens
the next-development PR. These publication operations are not performed here.

The workflow generates `release-notes.md` from commit subjects; it does not read the
curated `release_notes.md` in this preparation. Incorporate this draft explicitly
in the publication review or make a separately tested workflow change before
publication if automated use is desired. Do not assume it is automatically consumed.

Do not create a `release-request/**` branch or `.github/release-request` marker
during preparation: that existing push path initiates publication with no dry-run
input. Marketplace/Zenodo verification follows the existing publication workflow.
