Mining rules from Git changes

Refactoring Mining looks at concrete source changes and asks whether a change can be expressed as a reusable TriggerPattern DSL rule. The LLM proposes the generalization; Sandbox validates the returned DSL before presenting it as a candidate.

Mine commit history

  1. Open Window > Show View > Other... > Sandbox > Refactoring Mining.
  2. Choose Analyze Project... in the view toolbar.
  3. Select the Git-backed workspace project whose history you want to inspect. The view identifies the selected repository in its description instead of silently choosing the first open project.
  4. Inspect the commit table. The columns identify the commit, message, number of changed Java files, and AI analysis status.
  5. Select a commit with inferred rules to inspect the proposed DSL and its validation state.
  6. Check only the candidate rules you want to keep and choose Export selected as .sandbox-hint.

Mining is an analysis aid, not an automatic semantic proof. A green or valid DSL result means that the rule is syntactically accepted by the DSL validator; it does not prove that every future match preserves program behavior.

What is sent to rule inference?

For each changed Java file, Sandbox reconstructs a unified diff from the commit. That diff is passed to the shared rule-inference engine. Non-Java changes are not part of this mining path.

commit
  |- Java file diff 1 --> infer candidate rule --> validate DSL
  |- Java file diff 2 --> infer candidate rule --> validate DSL
  `- ...

Mine a selected unified diff

If you already have a unified diff, you do not need to scan repository history:

  1. Open or paste the diff into an Eclipse text editor.
  2. Select the complete diff text.
  3. Invoke Sandbox TriggerPattern > Mine DSL rule from diff....
  4. Sandbox runs inference in a background job.
  5. When a rule is produced, a new .sandbox-hint file is created in the workspace and opened for review.

The direct diff command still needs a clearer destination choice when several projects are open. The Refactoring Mining view now has explicit project selection; direct-command destination handling is tracked separately as QA work.

Example

A commit that repeatedly replaces a charset name with a typed constant could contain a change like this:

-new String(bytes, "UTF-8")
+new String(bytes, StandardCharsets.UTF_8)

The useful mining result is not a copy of that one edit. It is a generalized rule that captures the replaceable expression and the conditions under which the replacement is safe.

Current QA note: Working Tree command

The command currently named Mine DSL rules from working tree... does not yet analyze uncommitted working-tree changes; its implementation reads HEAD. Until that mismatch is fixed, use commit mining or a selected unified diff when you need a documented and reproducible before/after source.
