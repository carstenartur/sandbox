Platform Status: reference

Status applicability

A Status proposal requires all of the following:

  • the constructed type resolves exactly to org.eclipse.core.runtime.Status;
  • the constructor has five arguments;
  • severity resolves to INFO, WARNING, or ERROR;
  • code resolves at compile time to IStatus.OK.

Factory applicability

The native cleanup uses a factory only when every additional proof succeeds:

  • the project contains a readable META-INF/MANIFEST.MF with a runtime identity from Bundle-SymbolicName, or from Fragment-Host for a fragment;
  • the identity is a matching compile-time String constant or the exact enclosing class literal;
  • omitting the identity expression does not remove observable evaluation;
  • the required static factory overload exists in the resolved Status API;
  • message and throwable can be represented by that overload;
  • the factory return type is assignment-compatible with the source target.

When any factory proof fails, the proposal uses the four-argument constructor and retains the explicit identity. This fallback is still a useful cleanup because the proven redundant OK argument is removed.

Factory overload boundary

  • The one-argument overload may omit only a literal null throwable.
  • The two-argument overload preserves a non-null throwable or an explicit null when needed for return-type compatibility.
  • INFO with a non-null throwable remains a constructor when no equivalent overload exists.
  • The API is read from project bindings; availability is not inferred merely from the configured Java language level.

MultiStatus applicability

The constructed type must resolve exactly to org.eclipse.core.runtime.MultiStatus. Only a code whose compile-time value is zero and which is not already the canonical IStatus.OK reference is normalized. Nonzero, unresolved, and runtime-computed codes remain unchanged.

Bundled TriggerPattern boundary

The bundled hint has no project manifest and target-type proof. It never performs a Status constructor-to-factory replacement; it retains the explicit identity and removes only the redundant OK argument. The general Platform Logging hint contains no such Status rules.

Known limitations

  • Only PDE-style manifest metadata at META-INF/MANIFEST.MF is used.
  • Getter purity and class-initialization equivalence are not analyzed.
  • Only the exact enclosing class literal is accepted as a Class proof.
  • Custom subclasses and indirect factory wrappers are outside the matching scope.
  • Applicability and rejection reasons are not yet exposed as a public machine-readable report.

Support information

When reporting a problem, include the Sandbox feature version, Eclipse version, Java version, the project's Bundle-SymbolicName, the smallest reproducing source, the expected target type, and whether bindings were available.
