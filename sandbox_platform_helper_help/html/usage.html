Using Platform Status

Entry point

Open Java > Code Style > Clean Up, edit a cleanup profile, and select Platform Status (Sandbox). The configuration preview illustrates the two safe targets. The execution preview shows the actual combined source diff for each selected file.

Factory when identity is proven

Assume the project manifest declares Bundle-SymbolicName: com.example.plugin and the plug-in id is a compile-time String constant with that value.

Before

import org.eclipse.core.runtime.IStatus;
import org.eclipse.core.runtime.Status;

private static final String PLUGIN_ID = "com.example.plugin";

IStatus status = new Status(
    IStatus.ERROR,
    PLUGIN_ID,
    IStatus.OK,
    "Could not load preferences",
    exception);

After

import org.eclipse.core.runtime.IStatus;
import org.eclipse.core.runtime.Status;

private static final String PLUGIN_ID = "com.example.plugin";

IStatus status = Status.error(
    "Could not load preferences",
    exception);

No status information is lost. The selected factory supplies severity ERROR and code IStatus.OK; the calling bundle supplies the already-proven same plug-in identifier; message and throwable remain unchanged.

For a fragment project, the runtime bundle identity comes from Fragment-Host. A constant equal to the host symbolic name may use the factory; a constant equal only to the fragment symbolic name stays in the constructor fallback.

The exact enclosing class literal is another supported proof. Inside MyView, a constructor using MyView.class may use the corresponding factory when the factory return type fits the source context.

Constructor fallback when identity is not proven

Before

import org.eclipse.core.runtime.IStatus;
import org.eclipse.core.runtime.Status;

IStatus status = new Status(
    IStatus.WARNING,
    responsiblePluginId,
    IStatus.OK,
    "Extension failed",
    exception);

After

import org.eclipse.core.runtime.IStatus;
import org.eclipse.core.runtime.Status;

IStatus status = new Status(
    IStatus.WARNING,
    responsiblePluginId,
    "Extension failed",
    exception);

The explicit identity is retained for delegated, mismatching, dynamic, or unresolved expressions and when project bundle metadata is unavailable.

Why a matching getter is retained

A call such as JavaPlugin.getPluginId() is not erased merely because its expected return value equals the bundle symbolic name. Evaluating the method and initializing its declaring class can be observable. The cleanup therefore uses the constructor fallback unless both value and evaluation equivalence are proven.

Factory overload and result type

The cleanup resolves the actual Platform API on the project's build path. It uses a factory only when the required overload exists and its return type is assignment-compatible with the surrounding source target.

  • A literal null throwable may use a one-argument factory.
  • A non-null throwable requires a corresponding two-argument factory.
  • An INFO status with a non-null throwable retains the constructor when no equivalent INFO overload exists.
  • A factory returning IStatus is not inserted into a source context that requires concrete Status.

Compile-time code evaluation

Applicability is based on resolved integer values rather than source spelling. These are equivalent OK-code candidates:

IStatus.OK
0
private static final int OK_CODE = 0;

Nonzero and runtime-computed codes remain unchanged:

APPLICATION_SPECIFIC_CODE
computeStatusCode()
17

MultiStatus

A MultiStatus may carry an application-specific code. The cleanup changes only a compile-time value of zero to the named constant.

Before

import org.eclipse.core.runtime.IStatus;
import org.eclipse.core.runtime.MultiStatus;

MultiStatus status = new MultiStatus(
    pluginId,
    0,
    "Several operations failed",
    exception);

After

import org.eclipse.core.runtime.IStatus;
import org.eclipse.core.runtime.MultiStatus;

MultiStatus status = new MultiStatus(
    pluginId,
    IStatus.OK,
    "Several operations failed",
    exception);

When no change is made

  • The constructed type is not exactly the supported Status or MultiStatus type.
  • Type or constant bindings cannot be resolved.
  • The status code is nonzero or computed at runtime.
  • The severity is unsupported, for example IStatus.CANCEL.
  • The constructor is already in a supported shorter form.
  • The project does not satisfy the cleanup's compatibility gate.

Native cleanup and bundled hints

The native cleanup has project metadata and target-type information and can therefore choose a proven factory. The bundled TriggerPattern hint remains conservative and only removes the redundant OK argument while retaining the explicit identity.

Recommended workflow

  1. Enable Platform Status (Sandbox) in a dedicated cleanup profile.
  2. Run Source > Clean Up... on a small, version-controlled selection.
  3. Inspect each file in the real execution preview.
  4. Compile and run status-handling and logging tests.
  5. Use the standard Eclipse Undo operation when required.
