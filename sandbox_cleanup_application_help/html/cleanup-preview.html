Cleanup preview model

The cleanup workflow has two distinct previews:

  • The profile configuration tab preview is a small static example for the selected options.
  • The real execution preview shown after Source > Clean Up... lists concrete files and displays their proposed source comparison.

A configuration-tab screenshot is not evidence of an executable code change and must not be documented as one.

Standard local Cleanup changes

For ordinary local changes, Eclipse's standard LTK preview exposes affected files. Selecting a file updates the source comparison to the combined diff produced by all enabled applicable cleanup options for that file. Files with independent changes may be deselected independently; only the selected complete file changes are applied. Undo restores the applied operation.

The installed JFace Cleanup Help contains three SWTBot-generated captures of this real workflow: a combined single-file diff, another selected file's diff, and a multi-file preview with one file deliberately deselected. The same SWTBot scenario applies the changes and verifies byte-exact Undo.

This representative host-level proof is shared by local Cleanup families. Their own Help pages use compact before/after examples to document feature-specific source semantics instead of duplicating the same LTK frame.

Coordinated multi-file migrations

Some migrations are proven safe only as a closed set of changes across several Java files. With the pinned optional patched JDT UI host, each such set appears as one candidate-level checkbox leaf:

  • All required files and nested edits in one candidate are enabled or disabled together.
  • Required files and atomicity details remain visible for review.
  • Disjoint candidates are independently selectable.
  • A partially disabled nested change is rejected before execution and by direct perform validation.
  • Applying and undoing a candidate changes and restores all participating files together.
  • Save actions remain single-file and do not use this coordinated preview path.

See the installed Int-to-Enum Help and JUnit Migration Help for real SWTBot-generated atomic candidate screenshots and transformation-specific applicability rules.

Product boundary

Candidate-level atomic selection is an optional host capability supplied by the pinned patched org.eclipse.jdt.ui product. Sandbox cleanup bundles remain loadable on stock Eclipse through a dependency-free reflective bridge, but stock Eclipse does not enforce this candidate contract. Documentation and screenshots must identify the patched-product boundary rather than implying that every Eclipse host has the same behavior.
