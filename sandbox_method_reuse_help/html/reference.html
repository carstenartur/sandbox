Method Reuse: reference

Repeated-sequence mode

Input
Two or more contiguous statement sequences with at least the configured minimum length.
Selection
The candidate with the greatest statement-count multiplied by the number of replaceable duplicates; longer and earlier candidates win deterministic ties.
Transformation authority
Eclipse JDT ExtractMethodRefactoring with duplicate replacement enabled.
Output
One private extracted method and calls replacing every duplicate that JDT validates.

Existing-method mode

This separate mode replaces an inline sequence with an already available compatible method call. It does not create a new target method.

Safety model

Candidate discovery groups only sequences with compatible statement shapes. This is a performance filter, not a proof. JDT then checks binding-resolved local mappings, inputs, outputs, return handling, control-flow transfer, static context, checked exceptions, destination legality, visibility, and method conflicts. Any JDT error rejects the candidate without source changes.

Known limitations

  • Duplicate replacement is currently scoped to one enclosing type and compilation unit.
  • One independent extraction is performed per Cleanup run to avoid composing edits calculated from stale source.
  • Anonymous-class extraction and cross-type common-method placement are not yet automatic.
  • Sequence discovery considers up to twenty statements per candidate and a bounded number of JDT validation attempts per compilation unit to keep interactive Cleanup responsive.
  • The cleanup is not offered as a save action.

Support information

The Help content is shipped with the same feature version as the runtime plug-in. When reporting a problem, include the Sandbox feature version, Eclipse version, Java version, configured minimum length, the smallest reproducing source, and whether bindings were available.
