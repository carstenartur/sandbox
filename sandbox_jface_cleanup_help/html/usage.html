Using JFace API Modernization

Entry point

Open Java > Code Style > Clean Up, edit a cleanup profile, select JFace Cleanup (Sandbox), and enable only the independent migrations you intend to review.

SubProgressMonitor to SubMonitor

The cleanup joins the parent task declaration and its child-monitor allocations into the modern SubMonitor protocol.

Before

monitor.beginTask("Import", 100);
IProgressMonitor child =
    new SubProgressMonitor(monitor, 40);

After

SubMonitor subMonitor =
    SubMonitor.convert(monitor, "Import", 100);
IProgressMonitor child = subMonitor.split(40);

Several children sharing the same parent task use the same generated SubMonitor. Existing local names are respected. Supported style flags are mapped where an equivalent SubMonitor flag exists; review label-related legacy flags because the old and new APIs do not expose an identical presentation contract.

ViewerSorter to ViewerComparator

Binding-resolved uses of the deprecated sorter family are migrated to the corresponding comparator family.

Before

import org.eclipse.jface.viewers.ViewerSorter;

class NameSorter extends ViewerSorter {
}

After

import org.eclipse.jface.viewers.ViewerComparator;

class NameSorter extends ViewerComparator {
}

The cleanup also handles supported declarations, constructor calls, parameters, return types, and casts. JFace, Common Navigator, and tree-path variants are mapped only when the exact source type has a known replacement. Unresolved or custom sorter types remain unchanged.

ImageData to ImageDataProvider

A locally constructed ImageData used by one image creation can be moved into an SWT ImageDataProvider. This gives SWT a zoom-aware provider boundary rather than one eagerly created data object.

Before

PaletteData palette = new PaletteData(new RGB(0, 0, 0));
ImageData imageData = new ImageData(1, 1, 1, palette);
Image image = new Image(device, imageData);

After

PaletteData palette = new PaletteData(new RGB(0, 0, 0));
Image image = new Image(device,
    (ImageDataProvider) zoom -> {
        return new ImageData(1, 1, 1, palette);
    });

The source ImageData must be a removable local value whose construction can be reproduced safely inside the provider. Parameters, values used more than once, multi-fragment declarations, escaping values, and unresolved constructor bindings are deliberately left unchanged.

When a migration is offered

Each migration is independent. It is offered only when the relevant source types and invocations resolve to supported Eclipse APIs and the complete local rewrite can be produced without guessing.

Recommended workflow

  1. Enable one or more of the three migrations in a dedicated cleanup profile.
  2. Run Source > Clean Up... on a small, version-controlled selection.
  3. Use the execution preview to inspect each labelled JFace step and its concrete diff.
  4. Deselect an independent file or step when it is not appropriate for the current change.
  5. Compile and run progress-reporting, viewer-ordering, and SWT image tests before expanding the scope.

Real execution preview (LTK)

The profile tab preview is an example snippet. The actual execution preview appears after Source > Clean Up... and lists the concrete file and step changes that will be applied.

Independent local changes may be deselected per file or per step. Coordinated multi-file migrations use a separate atomic-selection contract tracked by carstenartur/sandbox#1451.
